아동용 영어 동화를 생성하는 모델을 다루면서 가장 먼저 막힌 곳은 채점이었습니다. 모델 A와 모델 B가 동화를 한 편씩 썼을 때, 어느 쪽이 더 잘 썼는지 잴 방법이 필요했습니다.

수학 문제라면 정답과 비교하면 됩니다. 하지만 동화에는 정답이 없습니다. 사람이 읽으면 되지만, 모델 후보가 10개가 넘고 프롬프트가 수십 개면 혼자서는 다 읽을 수 없습니다. 그래서 6월 중순부터 평가 시스템을 직접 만들기 시작했습니다. 벤치마크가 있는데 왜 직접 만들었는지는 [1편](/posts/why-build-own-eval-system/)에 적었습니다. 아래에서는 처음에 평가 방식을 어떻게 골랐는지와 첫 파이프라인의 구조를 정리했습니다.

## 1. 루브릭 절대 점수의 한계

처음 계획은 루브릭 채점이었습니다. 흥미도, 구성, 영어 자연스러움 같은 축을 정하고, 심판 <span class="term" data-tip="Large Language Model. 많은 텍스트에서 토큰의 조건부 분포를 학습해 문장을 생성하거나 분류·요약·추론 작업을 수행하는 언어 모델을 뜻한다.">LLM</span>이 축마다 1~5점을 매기는 방식입니다. 실제로 6월 16일에 <span class="term" data-tip="평가할 기준과 각 기준의 판단 수준을 미리 적은 채점 지침. 이름만 나열하지 않고 기준 설명과 점수 앵커를 함께 줘야 평가자마다 뜻이 달라지는 문제를 줄일 수 있다.">루브릭</span> 초안(`rubric.yaml`)부터 만들었습니다.[^repo]

그런데 자료를 조사할수록 절대 점수 채점의 한계가 보였습니다. 원리 문서에 정리해 둔 이유는 다음 네 가지입니다.

1. 점수 포화: 상위권 모델은 절대 루브릭에서 모두 만점 근처(4.8, 4.9, 5.0)에 몰려 작은 차이가 뭉개집니다. 창작 벤치마크 <span class="term" data-tip="LLM의 창작·감성 능력을 재는 공개 벤치마크. 창작 부문 v3는 심판 LLM의 pairwise 비교를 Glicko 레이팅으로 집계한다. v2가 상위권에서 포화되자 pairwise로 전환했다.">EQ-Bench</span>도 v2에서 이 문제를 겪고 v3에서 <span class="term" data-tip="후보를 둘씩 제시하고 어느 쪽을 선호하는지 기록하는 비교 방식. 절대 점수보다 판단 부담을 줄일 수 있지만 순서 효과와 평가자 편향은 별도로 통제해야 한다.">pairwise</span>로 옮겼습니다.[^eqbench]
2. 척도 해상도: 1~5 정수는 칸이 5개뿐이라 동점이 많이 나옵니다.
3. 기준 <span class="term" data-tip="반복 생성이나 편집을 거치며 대상의 속성이 조금씩 원래 값에서 멀어지는 현상. 직전 결과를 입력으로 다시 쓰는 구조에서는 오차가 누적될 수 있다.">드리프트</span>: 답을 하나씩 따로 보면 기준이 매번 흔들립니다. 같은 글이 어제와 오늘 다른 점수를 받습니다.
4. 평가자 편향: 심판이 관대한지 엄격한지가 점수에 그대로 묻어납니다.

두 사람의 키를 따로 맞히기는 어렵지만, 나란히 세워 놓고 누가 더 큰지 고르기는 쉽습니다. pairwise 비교는 점수 대신 둘 중 어느 쪽이 나은지를 묻습니다. 이 직관을 측정 모형으로 만든 것이 Thurstone의 1927년 비교판단 법칙입니다.[^thurstone] Bradley-Terry는 이 계보에서 나온 모델로, 두 후보의 실력 차이를 승률로 바꿔 줍니다.

그래서 순위는 pairwise로 내기로 했습니다. 루브릭 축은 버리지 않고 진단용으로 남겼습니다. "누가 더 나은가"와 "어디가 약한가"를 따로 묻는 구조입니다. <span class="term" data-tip="사용자가 익명화된 두 모델 응답을 비교해 투표하는 공개 평가 플랫폼의 초기 이름. 현재 LMArena는 대규모 사람 선호 데이터를 Bradley–Terry 계열 모델로 집계한다.">Chatbot Arena</span>는 전체 선호를 Bradley-Terry로 집계하고, EQ-Bench v3는 포화 때문에 pairwise로 넘어갔습니다. 두 곳이 각자 같은 결론에 도달해 있었다는 점이 결정의 근거가 됐습니다.[^arena][^mtbench]

## 2. Bradley-Terry 모델

pairwise로 판정을 모으면 승패 기록이 쌓입니다. 이 기록을 한 줄 순위로 바꾸는 표준 도구가 <span class="term" data-tip="맞대결 승패만으로 각 후보의 숨은 실력을 추정하는 통계 모델(1952). 실력 차가 승률을 정한다고 가정하고, 관측된 모든 승패를 가장 잘 설명하는 실력값을 최우도로 찾는다. 경기 순서와 무관하게 같은 답이 나오는 배치 방식이라, 고정된 대전 기록의 순위에 적합하다.">Bradley-Terry</span>(<span class="term" data-tip="Bradley–Terry 모델의 약칭. 두 후보의 상대적 실력으로 맞대결 승률을 설명하고 전체 pairwise 결과에서 실력값을 추정한다.">BT</span>) 모델입니다.[^bt1952] 모델마다 숨은 실력 β가 있다고 보고, "실력 βᵢ인 모델이 βⱼ를 이길 확률 = pᵢ/(pᵢ+pⱼ)"라고 가정합니다. 그리고 관측된 승패 전체를 가장 잘 설명하는 β를 <span class="term" data-tip="관측된 데이터가 나올 확률(우도)을 가장 크게 만드는 파라미터를 답으로 고르는 추정 원리. MLE라고도 한다. 데이터를 가장 잘 설명하는 값이라는 뜻이라, 통계 추정의 기본 잣대로 쓰인다.">최우도</span>(<span class="term" data-tip="Maximum Likelihood Estimation의 약칭. 관측된 데이터의 우도를 가장 크게 만드는 파라미터를 선택하는 최우도 추정이다.">MLE</span>)로 찾습니다.

### 2-1. MM 알고리즘 구현

구현은 Hunter(2004)의 <span class="term" data-tip="어려운 목적함수 대신 현재 점에서 맞닿는 대리함수를 반복 최적화하는 Majorization–Minimization 계열 방법. Hunter(2004)의 Bradley–Terry 갱신은 매 반복 우도가 감소하지 않도록 구성된다.">MM 알고리즘</span>을 사용했습니다.[^hunter] 핵심 반복은 다음과 같습니다.

```python
# eval/aggregate/bradley_terry.py — MM 반복 (Hunter 2004)
# p_i ← (W_i + prior) / [ Σ_j n_ij/(p_i+p_j) + 2·prior/(p_i+1) ]
for _ in range(max_iter):
    new = {}
    for i in models:
        denom = sum(nij / (p[i] + p[j]) for j, nij in games[i].items())
        denom += (2.0 * prior) / (p[i] + 1.0)   # 약한 anchor prior
        new[i] = (wins[i] + prior) / denom
    # 매 반복 기하평균=1 정규화 → mean(β)=0
```

`prior`는 무패나 전패인 모델의 점수가 무한대로 튀지 않게 잡아 주는 약한 가정입니다. 강도 1.0인 가상 상대와 무승부 1판을 섞는 것과 같습니다. 최종 점수는 체스 레이팅처럼 읽히도록 `Arena = 1000 + (400/ln10)·β`로 변환했습니다. 점수 차가 100이면 승률 약 64%, 400이면 약 91%입니다.

### 2-2. Elo 대신 BT를 고른 이유

<span class="term" data-tip="경기가 끝날 때마다 결과와 기대승률의 차이만큼 점수를 즉시 조정하는 체스식 레이팅. 실력이 변하는 선수를 추적하는 데 좋지만, 경기 순서에 따라 최종 값이 달라져 고정된 대전 기록의 순위에는 부적합하다.">Elo</span>도 후보였습니다. Elo는 경기가 끝날 때마다 레이팅을 갱신하는 온라인 방식이라, 같은 경기를 다른 순서로 넣으면 최종 값이 달라집니다. 제가 하려던 일은 정해진 모델 셋을 오프라인으로 한꺼번에 평가하는 것이었습니다. 그래서 순서와 상관없이 승패 전체를 한 번에 설명하는 BT가 맞다고 판단했습니다. Chatbot Arena도 2023년 12월에 Elo에서 BT로 바꿨습니다.[^arena]

### 2-3. 구현하면서 확인한 네 가지

구현하면서 확실히 정리해 둔 지점이 네 개 있습니다. 나중에 버그를 잡을 때도 이 네 가지를 다시 꺼내 썼습니다.

첫째는 목적함수입니다. <span class="term" data-tip="집계의 최소 단위. 한 쌍에 대한 한 심판의 판정 하나(양방향 평균을 마친 점수)를 말한다. 심판 셋이 본 쌍이면 contest 3개가 BT에 들어간다.">contest</span> 하나(모델 i가 j를 상대로 점수 s를 얻음)의 우도는 `[p_i/(p_i+p_j)]^s · [p_j/(p_i+p_j)]^(1-s)`이고, 전체 로그우도를 최대화하는 p를 찾는 것이 BT 적합입니다. Hunter의 MM은 반복할 때마다 이 로그우도를 단조증가시킵니다. 수렴 판정(연속 반복 간 최대 변화 < 1e-9)을 걸어 두면 멈춘 지점이 MLE입니다.[^hunter]

둘째는 식별 제약입니다. p 전체에 상수를 곱해도 BT 확률은 그대로이고, β로 보면 통째로 평행이동해도 바뀌지 않습니다. 이대로는 해가 하나로 정해지지 않아서, 매 반복 기하평균을 1로 맞추는 제약을 걸었습니다. 그러면 β 평균이 0이 되고 Arena 평균은 정확히 1000이 됩니다. "평균 1000짜리 리그"라는 해석이 수식으로도 성립합니다.

셋째는 스케일입니다. `400/ln10`으로 잡으면 <span class="term" data-tip="이 시스템의 최종 점수. BT로 추정한 실력값을 체스 레이팅처럼 읽히도록 평균 1000 기준으로 변환한 것. 두 모델의 점수 차가 곧 승률로 환산된다(차이 100이면 약 64%, 400이면 약 91%).">Arena 점수</span> 차가 Δ일 때 BT 승률이 정확히 `1/(1+10^(-Δ/400))`이 됩니다. 체스 Elo의 기대승률 공식과 같은 형태라 레이팅을 읽던 감각을 그대로 쓸 수 있습니다. Δ=100이면 0.640, Δ=400이면 0.909입니다. 이 두 값은 회귀 테스트에 상수로 넣어 두어서, 변환 코드를 건드리면 테스트부터 실패합니다.

넷째는 무승부 처리입니다. 위 우도에 s=0.5를 넣으면 무승부 하나를 반승 반패로 계산하고, 로그우도는 유한하게 나옵니다. 다만 순수 BT에는 무승부가 일어날 확률이라는 개념이 없습니다. 동점 성향까지 추정하는 3결과 모형과는 다릅니다. 점수가 발산하는 경우는 따로 있는데, 무패나 전패처럼 완전히 갈린 데이터에 prior가 없을 때입니다. 그래서 v1.1 분석 러너에는 무승부 성향을 파라미터 δ로 직접 모델링하는 <span class="term" data-tip="Bradley-Terry에 무승부 확률을 정식 파라미터로 추가한 확장 모델(1970). 순수 BT는 무승부 확률이 0이라, 무승부가 있는 데이터를 엄밀히 다루려면 이런 확장이 필요하다.">Davidson</span> 확장을 넣었습니다. 주 순위(0.5 처리)와 동점을 고려한 순위가 갈리는지 함께 확인합니다.[^davidson] 지금까지 갈린 적이 없어서 본선 집계는 단순한 방식을 그대로 쓰고 있습니다.

### 2-4. 점수 대신 구간으로 보기: 부트스트랩 CI

1050과 1030의 20점 차이가 실력 차이인지 우연인지는 숫자만으로 알 수 없습니다. 동화를 몇 권 더 뽑았거나 심판이 애매한 쌍에서 반대로 골랐다면 뒤집혔을 수도 있습니다. Arena 점수는 점추정이라 이 정보를 주지 않습니다.

그래서 점수마다 95% 신뢰구간을 붙였습니다. 그런데 BT 실력값의 오차를 바로 주는 닫힌 수식이 없습니다. 이럴 때 쓰는 방법이 부트스트랩입니다. 절차는 다음과 같습니다.

1. 가진 판정 데이터가 모집단을 대표한다고 보고, 복원추출로 가짜 데이터셋을 만듭니다. 실험을 한 번 더 했다면 나왔을 데이터를 흉내 내는 것입니다.
2. 가짜 데이터셋마다 BT를 처음부터 다시 적합해 Arena 점수를 계산합니다.
3. 이 과정을 1,000번 반복하고, 점수 분포의 2.5백분위와 97.5백분위 사이를 95% <span class="term" data-tip="Confidence Interval의 약칭. 이 글에서는 추정 불확실성을 나타내는 신뢰구간을 뜻하며 CI/CD의 CI와는 다른 용어다.">CI</span>로 씁니다.

분포를 따로 가정하지 않는 비모수 방법입니다.

두 모델의 주변 CI가 겹치면 우열을 단정하지 않습니다. 보수적으로 정한 규칙입니다. 반대로 겹치지 않는다고 유의성 검정을 마친 것도 아닙니다. 그렇게 말하려면 같은 재표집 안에서 점수 차의 분포를 직접 계산해야 하고, 여러 모델쌍을 한꺼번에 볼 때는 다중비교도 통제해야 합니다. 이 CI는 나중에 은퇴 판정(4편)까지 좌우하기 때문에 계산 단위와 조건도 여기에 적어 둡니다.

2026-07-20에 원자료를 다시 확인하면서, 797쌍·2,391 contest가 독립 관측 2,391개가 아니라는 점을 한 번 더 확인했습니다. 고유 동화는 142편뿐이고, 같은 동화가 상대만 바꿔 여러 비교에 들어갑니다. 독립 프롬프트는 13개입니다. 그래서 운영용 공식 CI는 검증된 쌍-군집 방식을 유지하고, 프롬프트-군집 CI를 보고용으로 함께 적습니다. 프롬프트가 10개 미만이면 "불안정"을 표시합니다. <span class="term" data-tip="이 프로젝트의 은퇴 스케줄러. 배치(5권)마다 BT와 CI를 갱신하고, CI 분리가 2연속 확인된 모델만 은퇴시킨다. 한 번의 우연으로 탈락시키지 않는 확인 절차가 이름의 유래다.">retire2</span>의 은퇴 경로는 부트스트랩에서 다시 시뮬레이션하지 않으므로, 적응형 런의 CI는 그 관측 경로에 조건부인 탐색 지표입니다.

### 2-5. 쌍 하나가 순위에 반영되는 과정

동화 쌍 하나가 순위에 들어가는 흐름은 그림 1과 같습니다.

![한 쌍의 판정이 양방향 swap과 다계열 jury를 거쳐 Bradley-Terry로 합쳐지는 흐름](/assets/img/posts/2026-07/pair-judgment-flow.svg)
_그림 1. 동화 쌍 하나가 순위에 반영되기까지. 심판마다 정방향과 역방향으로 2번 물어 평균 내고, 심판별 점수가 각각 하나의 contest로 BT에 들어간다._

동화 쌍(모델 a의 글 A, 모델 b의 글 B)은 심판 세 명에게 각각 전달됩니다. 심판마다 호출을 두 번 하는 이유는 순서 때문입니다. judge(A,B)와 judge(B,A)를 따로 물어 응답에서 승자를 파싱하고, 역방향 결과는 라벨을 뒤집어 정방향 기준으로 맞춥니다. 두 결과를 v(A)=1, v(tie)=½, v(B)=0으로 바꿔 평균 내면 그 심판의 점수 s가 됩니다. 가능한 값은 {0, ¼, ½, ¾, 1} 다섯 개입니다. 정방향에서 A가 이기고 역방향에서 B가 이기면 s=½가 되어, <span class="term" data-tip="내용과 무관하게 먼저 보여준 답을 더 좋게 평가하는 경향. LLM 심판에게 일관되게 관측되는 대표적 편향이라, 순서를 바꿔 두 번 묻는 통제가 필요하다.">위치 편향</span>이 만든 모순된 판정이 무승부로 상쇄됩니다.

심판 세 명의 s는 각각 contest (a, b, s) 하나가 되어 BT에 들어갑니다. 다수결로 합치지 않은 이유는 심판끼리 엇갈린다는 사실도 정보이기 때문입니다. 셋 중 둘이 A를 골랐다면 BT 우도에는 "2/3만큼 A 우세"로 반영됩니다. 마지막 단계의 MM 반복이 모든 프롬프트와 모든 쌍의 contest를 한 번에 설명하는 실력값 p를 찾고, 그 결과가 Arena 점수와 <span class="term" data-tip="가진 데이터에서 복원추출로 여러 번 가짜 표본을 만들어 같은 계산을 반복하고, 그 결과들의 흩어짐으로 추정치의 불확실성을 재는 방법. 표본이 모집단을 대표한다면 재표집의 흔들림이 실제 추정 오차와 비슷하다는 원리다.">부트스트랩</span> CI로 나옵니다.

이 구조에는 두 가지 원칙이 있습니다. 하나는 편향을 나중에 재서 빼지 않고 처음부터 상쇄하는 것입니다. 위치 편향의 크기를 재서 보정하는 대신, 두 방향으로 물어 평균 내는 계산이 자동으로 지우도록 했습니다.

다른 하나는 정보를 버리지 않는 것입니다. 다수결로 승자만 남기면 2대 1과 3대 0이 똑같이 한 표가 됩니다. 심판별 contest를 그대로 넣으면 그 차이가 우도에 남고, 최종 점수를 얼마나 믿을 수 있는지에도 반영됩니다.

## 3. 심판 편향 통제: 편향 네 가지와 통제 방법

LLM을 심판으로 쓰면 편향이 따라옵니다. 문헌에서 확인한 편향을 다음과 같이 구조로 막았습니다.

| 편향 | 통제 방법 |
|---|---|
| 위치 편향 (먼저 보인 글 선호) | 같은 쌍을 A,B / B,A 양방향으로 2번 물어 평균 |
| <span class="term" data-tip="LLM이 자기(또는 같은 계열 모델)가 쓴 글을 알아보고 더 높게 평가하는 편향. 심판과 후보가 같은 계열이면 그 쌍에서 심판을 제외하는 구조적 통제가 필요하다.">자기 선호</span> (자기 계열 모델 편애) | 심판이 후보와 같은 계열이면 그 쌍에서 자동 제외 |
| 단일 심판의 취향 | 서로 다른 계열 심판 여러 명(jury)의 판정을 각각 BT에 투입 |
| 장문 선호 | 판정 입력을 4,000자에서 절단 (양쪽 동일 적용) |

위치 편향과 장문 선호는 MT-Bench가 보고한 편향입니다.[^mtbench] <span class="term" data-tip="같은 두 답을 A/B와 B/A 순서로 각각 평가해 순서에 따른 변화를 확인하는 방법. 두 결과를 함께 쓰면 위치 편향을 줄일 수 있지만 완전히 없어진다고 보장되지는 않는다.">양방향 swap</span>은 A,B 순서와 B,A 순서를 모두 판정해 위치 효과를 줄입니다. jury를 여러 계열로 구성한 것은 PoLL 결과를 따른 것입니다. 단일 대형 심판보다 계열 편향이 적고 사람 판단과도 더 일치했다는 결과입니다.[^poll] 자기 계열 제외는 LLM의 자기 선호 편향 연구를 근거로 했고, 같은 계열 편향을 실제로 잰 값은 5편에 있습니다.

사람 평가는 같은 동화 쌍 일부에만 적용합니다. 전부 볼 수는 없기 때문입니다. `pair_id`로 짝을 맞춰 심판단과의 일치도(Cohen's κ)를 잽니다. 심판 LLM이 사람만큼 일관적인지 확인하는 <span class="term" data-tip="사람이 직접 평가한 소량의 기준 데이터. 같은 항목을 자동(LLM) 평가와 사람이 모두 평가하게 한 뒤 일치도를 재면, 자동 평가를 얼마나 믿어도 되는지가 숫자로 나온다.">골든셋</span>입니다.

## 4. 외부 패키지 없는 파이프라인

6월 18일에 첫 파이프라인을 커밋했습니다. 30개 파일, 1,732줄입니다.[^repo] 외부 패키지는 하나도 쓰지 않았습니다. numpy나 scipy 없이 Python 표준 라이브러리만으로 BT, 부트스트랩 <span class="term" data-tip="같은 절차로 표본을 반복 수집할 때 정해진 비율만큼 모수를 포함하도록 만든 구간. 두 개의 95% 신뢰구간이 겹치는지만으로 차이의 유의성을 판정할 수는 없다.">신뢰구간</span>, <span class="term" data-tip="두 평가자의 범주형 판정 일치도에서 주변분포로 기대되는 우연 일치를 보정한 계수. 1은 완전 일치, 0은 기대 일치 수준이며 음수도 가능하다.">Cohen's κ</span>, <span class="term" data-tip="두 변수의 순위를 비교하는 비모수 상관계수. 1은 같은 순서, -1은 완전히 반대 순서이며 0은 순위 사이의 단조 관계가 관측되지 않았다는 뜻이다.">Spearman</span> 상관을 직접 구현했습니다.

이유는 단순했습니다. 이 프로젝트는 멘토님께 검증받는 포트폴리오이기도 해서, 라이브러리 호출이 아니라 수식을 이해하고 구현했다는 것을 코드로 보여 주고 싶었습니다. 부수 효과도 있었습니다. Python 3.9 이상만 있으면 어느 컴퓨터에서든 `python eval/run_pipeline.py` 한 줄로 실행됩니다. 고정 시드 합성 데이터를 쓰는 mock 모드가 있어서 <span class="term" data-tip="소프트웨어가 다른 소프트웨어의 기능이나 데이터에 접근할 때 따르는 호출 계약. 사용할 주소, 입력 형식, 인증, 응답과 오류 규칙을 함께 정의한다.">API</span> 키 없이도 end-to-end가 <span class="term" data-tip="같은 입력과 상태에서 같은 결과를 내는 성질. 시드 고정은 난수 경로를 통제하는 한 조건일 뿐이며 구현·하드웨어·외부 서비스가 바뀌면 재현이 깨질 수 있다.">결정론적</span>으로 재현됩니다. 코드를 고칠 때마다 회귀 테스트 17개가 수식이 깨졌는지 확인합니다.

파이프라인은 다음 다섯 단계로 구성됩니다.

| 단계 | 하는 일 | 나오는 것 |
|---|---|---|
| 1. 생성(generate) | 모델별로 동화를 쓴다 | 모델별 동화 |
| 2. 판정(judge) | 쌍마다 양방향 swap으로 판정한다 | 쌍별 판정 |
| 3. 집계(aggregate) | BT를 적합하고 부트스트랩을 돌린다 | 점수와 95% CI |
| 4. 검증(validate) | 사람 골든셋과 비교한다 | κ |
| 5. 리포트(report) | 결과를 묶는다 | 리더보드 md/html/csv |

같은 날 브라우저용 UI(단일 <span class="term" data-tip="웹 문서의 구조와 의미를 요소로 표시하는 마크업 언어. CSS는 표현을, JavaScript는 동작을 주로 담당한다.">HTML</span> 앱)도 만들기 시작했습니다. 이 앱은 이후 파이썬 파이프라인과 별개로 브라우저에서 실측까지 수행하는 엔진으로 커졌습니다. 그 과정과 그 결정이 만든 문제는 3편에서 다룹니다.

만들기 전에 기존 시스템 세 개를 분석했습니다. 각각에서 가져온 것과 다르게 간 것은 다음과 같습니다. 다르게 간 이유는 대부분 아동 동화라는 도메인 때문입니다. 안전성, 연령 적합, 난이도 같은 축은 일반 벤치마크에 기준이 없어서 루브릭을 직접 만들어야 했습니다.

순위 계산은 Arena에서, pairwise로 옮긴 경험은 EQ-Bench에서, 루브릭 축은 G-Eval 계열에서 가져왔습니다. 개인 프로젝트에 사람 표가 수십만 개 있을 수는 없으니, 그 자리는 다계열 LLM jury와 편향 통제 구조, 소량 골든셋으로 채웠습니다. 이 구조가 실제로 버텼는지는 5편에서 숫자로 확인합니다.

## 마치며

순위는 pairwise와 BT로 내고, 루브릭은 진단에 쓰는 것으로 뼈대를 정했습니다. pairwise로 바꿨다고 기준이 필요 없어지지는 않았습니다. 2026-07-22의 후속 `childlit-v3`에서는 Python과 브라우저가 `rubric.yaml`의 같은 10축 criteria와 앵커를 쓰고, 원 생성 요청, 독서 방식, 목표 연령, 실측 단어 수를 심판에게 넘깁니다. 수치 <span class="term" data-tip="영어 독자의 읽기 능력과 텍스트 난이도를 같은 척도에 표시하는 상용 지표. 텍스트 측정은 어휘의 빈도와 문장 길이 같은 특성을 사용하며, 이 프로젝트의 가독성 공식 합성값은 공인 Lexile이 아니다.">Lexile</span>은 창작 본선과 심판에서 빼고 별도 <span class="term" data-tip="아이가 어른의 실시간 도움이나 낭독 없이 직접 글자를 해독하고 내용을 이어 가는 읽기 방식. 같은 아이도 읽어주는 글을 이해하는 수준과 혼자 읽는 수준이 다를 수 있다.">독립 읽기</span> 프로브에만 넣었습니다. 자동 계산한 <span class="term" data-tip="Flesch–Kincaid Grade Level. 문장당 단어 수와 단어당 음절 수로 영어 텍스트의 미국 학년 수준을 추정한다.">FKGL</span>·<span class="term" data-tip="글자 수와 문장 수를 사용해 영어 텍스트의 미국 학년 수준을 추정하는 가독성 지수. 음절 수를 직접 세지 않는다는 점이 FKGL과 다르다.">Coleman–Liau</span>·<span class="term" data-tip="Automated Readability Index. 단어당 글자 수와 문장당 단어 수로 영어 텍스트의 미국 학년 수준을 추정하는 공식이다.">ARI</span> 근사값도 순위와 은퇴에는 들어가지 않습니다. 바꾼 근거와 브랜치 상태는 [프롬프트 재설계 글](/posts/creative-ranking-reading-level-two-track/)에 따로 정리했습니다.
