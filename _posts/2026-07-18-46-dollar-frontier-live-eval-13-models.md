## 멈춘 이유는 API가 아니었다

"Unexpected end of <span class="term" data-tip="문자열·숫자·불리언·배열·객체·null을 표현하는 텍스트 데이터 형식. 주석과 trailing comma는 표준 JSON에 포함되지 않는다.">JSON</span> input"은 심판 API 응답 하나가 깨져서 난 파싱 오류다. 직접적인 계기는 그거였다. 그런데 파고들어 보니 런은 이미 몇 시간째 위험한 상태로 돌고 있었다.

앱은 이어하기 기능(3편) 때문에 1.5초마다 진행 상태를 <span class="term" data-tip="브라우저가 출처별로 제공하는 동기식 문자열 키-값 저장소. Web Storage 한도는 브라우저에 따라 다르고 한도를 넘으면 QuotaExceededError가 날 수 있어 큰 체크포인트 저장에는 맞지 않는다.">localStorage</span>에 저장한다. 이 실측을 돌린 브라우저에서는 한도가 약 10MB였다. 동화 원문과 심판 근거 전문까지 담으면 쌍당 약 13KB라 775쌍 근처에서 넘친다. 저장 코드는 이랬다.

```javascript
function saveState(){
  try{ localStorage.setItem("lb_eval_v1", JSON.stringify({...STATE, apiKey:""})); }
  catch(e){}   // 용량 초과 예외가 여기서 무시됐다
}
```

용량 초과 예외는 빈 catch에 삼켜졌다. <span class="term" data-tip="진행 상태를 통째로 저장해둔 지점. 중단되거나 크레딧이 떨어져도 완료분을 다시 호출하지 않고 그 지점부터 이어서 실행할 수 있다.">체크포인트</span>는 38쌍에서 멈춰 있었다. 그 뒤 $45어치 판정은 탭 메모리에만 있었던 거다. 멈췄을 때 탭이 살아 있어서 겨우 건졌다. 브라우저가 죽었으면 전부 날아갔다.

고친 건 세 가지다. 저장이 실패하면 로그에 경고가 뜨게 했고, 10쌍마다 <span class="term" data-tip="브라우저가 출처별로 제공하는 비동기 객체 데이터베이스. localStorage보다 큰 구조화 데이터를 다루지만 저장 한도와 삭제 정책은 브라우저·디스크 여유·사용자 설정에 따라 달라진다.">IndexedDB</span>와 GitHub에 자동 백업하게 했다. 진행 상황 전체를 파일로 내려받는 체크포인트 버튼도 달았다. IndexedDB도 브라우저마다 한도와 제거 정책이 있어서 파일과 원격 백업을 같이 둔다.

## 심판이 자기 계열 모델에 후했다 (t = 6.43)

부끄러운 실수가 하나 있었다. 자기 계열 심판 제외를 끈 채(allowSelfEval=true) 데이터를 모았다. 편향을 막는 장치를 빼먹은 건데, 역설적으로 그 덕에 자기 계열 편향을 모든 쌍에서 잴 수 있었다.

자기 계열이 낀 쌍의 평균 점수만 봐서는 모른다. 그 모델이 진짜 더 잘 썼을 수도 있으니까. 그래서 동료 심판을 대조군으로 썼다. 같은 쌍을 본 세 심판 중 한 명의 점수에서 나머지 둘의 평균을 뺀다(peer-relative Δ). 그러면 쌍의 실제 품질 차이는 빠지고 그 심판의 성향만 남는다. 이 Δ가 자기 계열 쌍에서 꾸준히 양수인지 <span class="term" data-tip="평균 차이를 표준오차와 비교해 귀무가설 아래에서 관측값이 얼마나 이례적인지 평가하는 검정. 유의성은 t값 하나가 아니라 자유도, 검정 방향, p값 또는 임계값과 함께 판단한다.">t-검정</span>으로 봤다.

| 심판 (계열) | 자기편애 Δ | t |
|---|---|---|
| GPT-5.4 (openai) | +0.029 | +1.58 |
| Claude Sonnet 4.6 (anthropic) | +0.056 | +2.95 |
| Gemini 2.5 Pro (google) | +0.095 | +5.97 |
| 3심판 합산 | +0.066 (≈ +15 Arena pt) | +6.43 |

세 심판 모두 자기 계열 쪽으로 양수였다. 합산 t=6.43이면 우연이라고 하기 어렵다. 제일 센 건 Gemini였다. 후보 중 구글 계열이 4개로 가장 많아서 표본도 영향도 컸다. 여러 계열 jury를 평균하면 일부는 상쇄되는데, 계열별 후보 수가 들쭉날쭉해서 다 지워지진 않는다.

2편에서 구조로 막겠다고 했던 편향이 실제로 잴 수 있는 크기로 있었다. 그래서 인접 순위(±15pt 이내)는 오차로 보기로 했다. 다음 런에서는 자기평가 제외를 꼭 켠다. <span class="term" data-tip="Large Language Model. 많은 텍스트에서 토큰의 조건부 분포를 학습해 문장을 생성하거나 분류·요약·추론 작업을 수행하는 언어 모델을 뜻한다.">LLM</span> 평가자가 자기 출력을 알아보고 점수를 더 주고, 자기 인식 능력이 강할수록 <span class="term" data-tip="LLM이 자기(또는 같은 계열 모델)가 쓴 글을 알아보고 더 높게 평가하는 편향. 심판과 후보가 같은 계열이면 그 쌍에서 심판을 제외하는 구조적 통제가 필요하다.">자기 선호</span>도 강하다는 연구가 있다.[^selfpref] 우리 데이터에서는 같은 회사 계열 모델 사이에서도 그게 보였다.

## BT와 Elo가 다른 순위를 냈다 (Spearman 0.742)

앱은 주 순위(BT)와 보조 지표(순차 Elo)를 같이 보여 준다. 이번 런에서는 둘이 꽤 갈렸다. Claude 두 모델은 순서가 아예 뒤집혔다.

| 모델 | BT(Arena) 순위 | <span class="term" data-tip="경기가 끝날 때마다 결과와 기대승률의 차이만큼 점수를 즉시 조정하는 체스식 레이팅. 실력이 변하는 선수를 추적하는 데 좋지만, 경기 순서에 따라 최종 값이 달라져 고정된 대전 기록의 순위에는 부적합하다.">Elo</span> 순위 |
|---|---|---|
| Claude Opus 4.8 | 10위 | 4위 (6계단 위) |
| Claude Opus 4.7 | 4위 | 9위 (5계단 아래) |

retire2와 Elo의 궁합이 나빠서다. Elo는 모두 1000에서 시작해 경기마다 `R ← R + K·(s − E)`로 갱신하는 온라인 지표다(기대승률 `E = 1/(1+10^((R_상대−R)/400))`, K=32). 순서대로 갱신하다 보니 배치 2에서 은퇴한 모델의 Elo는 거기서 멈추고, 생존 모델만 계속 움직인다. 멈춘 값과 움직이는 값을 한 표에 놓고 비교하는 꼴이 된다. <span class="term" data-tip="Elo에서 경기 하나가 점수를 최대 몇 점까지 움직일 수 있는지 정하는 민감도 상수. 크면 최근 경기에 민감해지고 작으면 점수가 천천히 변한다.">K-팩터</span> 갱신은 그 순간 상대 레이팅에 민감해서, 타이밍 좋게 거둔 승리가 크게 잡히기도 한다. BT는 모델별 경기 수 불균형과 대전 시점을 <span class="term" data-tip="Maximum Likelihood Estimation의 약칭. 관측된 데이터의 우도를 가장 크게 만드는 파라미터를 선택하는 최우도 추정이다.">MLE</span>로 한꺼번에 처리하니 이런 문제가 없다.

2편에서는 이론만 보고 "오프라인 고정 셋에는 BT"를 골랐는데, 그 이유를 이번에 직접 봤다. Elo가 BT와 벌어진 건 데이터가 작고 retire로 대진이 짜였다는 진단 신호 정도로 읽었다.

## 신형 Opus가 구형보다 낮게 나왔다

리더보드에서 제일 눈에 걸린 건 Opus 4.8(953, 쌍-군집 CI 923–977)이 Opus 4.7(1052, 1023–1077)보다 낮게 나온 거였다. 두 주변 CI는 안 겹친다. 그렇다고 두 모델 차이를 정식으로 검정했다고 하긴 어렵다. 2026-07-20에 낸 프롬프트-군집 참고 계산(2,000회, <span class="term" data-tip="생성 시작점이 되는 난수의 초기값. 같은 모델과 같은 파라미터를 그대로 유지할 때 결과를 다시 만들어내는 재현 장치이며, 서로 다른 프롬프트 사이에서 특정 인물이나 화풍을 붙잡아 두는 기능은 아니다.">seed</span> 20260720)에서는 4.8이 834.5–1062.4, 4.7이 972.6–1138.8로 겹쳤다. 프롬프트가 13개뿐이고 은퇴 경로도 재시뮬레이션하지 않았으니 둘 다 확증 구간은 아니다. 독립 50프롬프트 완주 런에서 다시 볼 가설로 남겨 뒀다.

자기 계열 편향으로는 설명이 안 된다. 그 편향은 두 Opus를 똑같이 밀어준다. Opus끼리 붙을 때도 Anthropic 심판에게는 양쪽 다 같은 계열이라 상대적인 편향이 안 생긴다. GPT와 Gemini가 섞인 중립 판정에서, 아동 동화라는 도메인에 한해 신형이 낮게 나온 거다. 최신 모델이 늘 낫다는 가정이 도메인 특화 평가에서는 안 맞을 수도 있다. 도메인 탓인지 모델 회귀인지는 분리 실험을 해 봐야 안다.

## 비용과 토큰은 품질보다 더 크게 갈렸다

실측은 모델별 편당 생성 비용과 토큰도 같이 남긴다. 편당 생성 비용은 제일 비싼 Gemini 3.1 Pro가 약 $0.026, 제일 싼 Gemma 4 31B가 약 $0.0001이었다. 260배쯤 차이다(로컬 Gemma E4B는 $0).

품질이랑 겹쳐 보니 재미있었다. 4~5위로 서로 구별되지 않았던 Qwen3.6 35B가 편당 약 $0.004로, 품질이 비슷한 프론티어 모델보다 훨씬 쌌다. 앱의 품질×비용 Pareto 차트에서 왼쪽 위, 싸고 좋은 쪽에 붙어 있을수록 실서비스 후보로 본다.

토큰 쓰는 버릇도 달랐다. 같은 길이의 동화를 시켰는데 편당 토큰이 GPT-5.2는 약 430, Qwen3.5 122B는 약 4,500이었다. 10배가 넘는다. Qwen 계열은 생각한 걸 출력에 많이 남겨서 길어지고, 그게 고스란히 비용으로 찍힌다.

요청한 단어 수 구간(예: 30~50단어)을 지켰는지는 심판에게 묻지 않는다. 자동 이진 체크로 판정한다. <span class="term" data-tip="검증 가능한 지시를 포함한 프롬프트와 규칙 기반 채점기로 구성된 지시 준수 벤치마크. 사람이나 LLM 심판 대신 프로그램으로 조건 충족 여부를 확인한다.">IFEval</span>이 정리한 검증 가능 제약(verifiable instruction) 방식이다.[^ifeval] 난이도(적합도, 반응성)와 준수(단어 수, 안전)를 따로 재도록 난이도·효율 트랙을 짠 것도 이 때문이다.

## 부록: 지표가 전부 0으로 나온 이유

결과 화면의 난이도 적합도(Match Rate, MAE)가 모든 모델에서 0으로 나오는 버그도 이날 잡았다. 집계 함수 한 줄 중간에 `//` 주석이 박혀 있었다. 그 뒤 누적문 세 개가 통째로 주석이 됐는데, 문법상 멀쩡한 코드라 구문 검사는 통과했다. 죽은 코드는 에러를 안 낸다.[^bugfix]

고치고 다시 계산하니 <span class="term" data-tip="예측값과 실제값 차이의 절댓값을 평균한 지표. 작을수록 평균 오차가 작으며, 큰 오차를 제곱하는 RMSE와 달리 오차 크기에 선형으로 반응한다.">MAE</span> 380L, <span class="term" data-tip="목표 난이도의 허용 범위(±밴드) 안에 들어온 비율. 절대 눈금이 틀린 측정기로 재면 실력과 무관하게 낮게 나올 수 있다.">Match Rate</span> 2.9%가 나왔다. 이번엔 숫자가 낮은 게 측정 도구 쪽 문제였다. 측정한 <span class="term" data-tip="영어 독자의 읽기 능력과 텍스트 난이도를 같은 척도에 표시하는 상용 지표. 텍스트 측정은 어휘의 빈도와 문장 길이 같은 특성을 사용하며, 이 프로젝트의 가독성 공식 합성값은 공인 Lexile이 아니다.">Lexile</span> 중앙값이 868L로 목표(~500L)보다 계속 높았는데, 짧은 글에서는 <span class="term" data-tip="글을 얼마나 수월하게 읽고 이해할 수 있는지를 뜻한다. 문장·단어 표면값으로 계산한 가독성 공식은 정량 단서일 뿐 의미 구조, 배경지식, 독자와 읽기 목적 전체를 대신하지 않는다.">가독성</span> 공식이 난이도를 과대추정한다. 6편에서 자세히 다룬다.
