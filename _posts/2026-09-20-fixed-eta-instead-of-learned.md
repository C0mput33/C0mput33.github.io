그림책 생성 화면에는 남은 시간을 알려 주는 진행률 안내가 있습니다. 어느 날 이 안내가 "약 19분 남았어요"라고 표시했는데, 같은 날 같은 크기의 책을 실측해보니 9분 32초에 끝났습니다. 안내가 실제의 두 배였습니다.

아래에서는 두 배 차이가 난 원인과, 학습형 추정을 걷어내고 고정값으로 바꾼 과정을 정리했습니다.

## 1. 문제 상황: 안내 19분, 실제 9분 32초

인터뷰(사람이 답하는 시간)는 빼고 단계별 소요를 측정했습니다. 값은 워커 로그의 단계 시작·종료 타임스탬프와 관측 트레이스에서 가져왔습니다. 결과는 다음과 같습니다.

| 단계 | 소요 |
|---|---|
| 원고 생성(본문 24쪽 + 심사 3회 + 배역 점검 + 어휘 재작성) | 3분 57초 |
| 그림 단계 전체 | 5분 35초 |
| 표지·뒤표지 | 1분 48초 |
| 입력 심사 7건 병렬 | 9.4초 |
| 초판 <span class="term" data-tip="한 장의 이미지를 2×2로 나눠 네 쪽을 동시에 그리고, 받은 뒤 네 칸으로 잘라 각각의 쪽으로 쓰는 방식. 호출 한 번에 네 쪽을 처리해 쪽당 비용이 내려가지만, 칸 하나에 배정되는 출력 토큰은 단일 이미지보다 적다.">4칸 이미지</span> 7장 | 64.5초 |
| <span class="term" data-tip="생성된 결과물을 별도의 모델 호출로 검사해 통과 여부와 지적 사항을 돌려받는 단계. 안전, 글자 일치, 만듦새, 참조 일치처럼 항목을 나눠 둔다.">출력 심사</span> 7건 | 71.6초 |
| <span class="term" data-tip="심사가 지적한 자산만 골라 다시 생성하는 단계. 한 번만 수행하고 그 결과를 다시 심사하지 않으면, 교정이 빗나가도 그대로 출고된다.">재작화</span> 8장 | 59.7초 |
| 합계 | 9분 32초 |

전체는 9분 32초였고, 그중 그림 단계가 5분 35초로 가장 길었습니다.

## 2. 원인 분석: 75분위가 과거 표본을 따라간 이유

추정기는 최근에 완료한 책들의 소요를 표본으로 모아 평균과 <span class="term" data-tip="정렬한 값에서 위에서 25% 지점에 있는 값. 평균보다 느린 쪽을 더 반영해 보수적인 추정을 만들지만, 그만큼 과거의 느린 실행에 끌려간다.">75분위</span>로 기대 소요를 계산하고 있었습니다. 이미지 수가 비슷한 책끼리 비교하는 장치도 붙어 있었습니다.

확인해보니 문제는 표본이 과거 실행이라는 점이었습니다. 표본에는 표지 재시도가 잦던 시기와 그림을 순차로 그리던 시기의 실행이 섞여 있었습니다. 75분위는 그중 느린 쪽을 따라갑니다.

그사이 파이프라인에는 병렬 생성, 이미지 품질 고정, 심사 입력 축소가 들어갔습니다. 이런 변경이 안내에 반영되려면 새 표본이 충분히 쌓일 때까지 기다려야 했습니다.

학습형 추정은 환경이 안정적일 때 잘 맞습니다. 당시에는 파이프라인을 일주일에 몇 번씩 바꾸고 있었기 때문에, 과거 실행이 현재를 대표하지 못했습니다.

## 3. 해결 방법: 학습 대신 9분 고정값

### 3-1. 고정값 적용

학습을 걷어내고 설정값을 그대로 쓰도록 바꿨습니다. 적용한 규칙은 다음과 같습니다.

- 원고 240초 + 그림 300초 = 540초(9분)
- 이미지 수와 무관하게 같은 값을 씁니다. 표지를 먼저 그리고 나머지는 병렬로 그리기 때문에 소요가 장수에 거의 비례하지 않습니다. 실측에서도 24쪽 그림 단계가 5분 35초였습니다.
- 환경변수로 조정할 수 있습니다. 실제 소요가 달라지면 값 하나만 고치면 됩니다.

### 3-2. 학습 전용 코드 제거

학습에만 쓰이던 코드도 함께 지웠습니다. 조회 포트, 저장소 <span class="term" data-tip="동결한 베이스 모델 옆에 붙여 학습하는 작은 추가 가중치 묶음. 파일이 작아도 층 이름과 배열 모양이 실행 프레임워크의 형식과 맞지 않으면 그대로 옮겨 쓸 수 없다.">어댑터</span> 구현, 리포지토리 질의, 학습을 검증하던 테스트가 대상이었습니다. 남겨 두면 나중에 코드를 읽는 사람이 "이 값이 어디서 오는가"를 찾느라 두 경로를 모두 따라가야 합니다.

진행률 퍼센트 계산, 워커가 보고하는 완료 개수 반영, 완료 전 99% 상한은 그대로 두었습니다.

## 4. 트레이드오프

고정값으로 바꾸면서 추정이 더 이상 스스로 따라가지 않게 됐습니다. 파이프라인이 느려지거나 빨라지면 안내는 틀린 채로 남습니다. 그래서 "생성 구조를 크게 바꾸면 이 값도 함께 고친다"를 규칙으로 정하고, 코드 주석과 이슈 양쪽에 적어 두었습니다.

그래도 이 방식을 선택한 이유는 두 가지입니다. 사용자에게 중요한 건 추정 방식의 정교함이 아니라 안내가 맞는지입니다. 19분이라고 안내하고 9분 만에 끝나면 사용자에게는 틀린 안내일 뿐입니다. 또 지금은 파이프라인을 자주 고치는 시기라서 학습이 따라올 시간 자체가 없었습니다.

## 마치며

과거 실행으로 기대 소요를 학습하던 추정이 실제의 두 배를 안내했고, 원인은 느렸던 과거 실행이 표본에 오래 남는 구조였습니다. 학습을 걷어내고 실측에 맞춘 고정값 540초로 바꿨습니다.

파이프라인이 안정되면 학습형 추정으로 돌아갈 수 있습니다. 그때는 표본에 기간 상한을 두거나 코드 릴리스 이후의 실행만 쓰도록 해서, 오래된 기록을 먼저 끊어 낼 계획입니다.
