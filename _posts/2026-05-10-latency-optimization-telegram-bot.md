Telegram 봇의 평균 응답 시간은 4.2초, P95는 8.7초였다. 7일 기준선 로그 218건을 확인한 뒤 멀티 모델 <span class="term" data-tip="들어온 요청을 여러 서버·모델·공급자 후보 중 하나로 보내는 선택 과정. 가용성, 현재 부하, 비용, 캐시 재사용 가능성처럼 목적에 맞는 기준과 실패 시 대체 경로가 필요하다.">라우팅</span>과 <span class="term" data-tip="반복되는 프롬프트 앞부분의 계산 결과를 재사용해 지연이나 입력 비용을 줄이는 기능. 자동·명시형 여부, 최소 길이, 만료 시간, 할인율은 모델과 공급자마다 다르다.">프롬프트 캐싱</span>을 적용했다. 이후 2주 로그에서 평균은 1.8초, P95는 3.1초로 내려갔다. 아래에는 어떤 조건에서 쟀는지, 두 변경이 각각 무엇을 줄였는지, 아직 남아 있는 오분류와 <span class="term" data-tip="요청한 데이터나 프롬프트 상태가 캐시에 없어 원래 계산이나 저장소 조회를 다시 수행하는 경우. 캐시 키·만료·라우팅이 달라져도 발생할 수 있다.">캐시 미스</span> 문제를 적었다.

## 기준선 측정

개선 전 7일간의 메시지 로그를 봤다(n=218).

| 지표 | 값 |
|------|-----|
| 평균 응답 시간 | 4.2초 |
| <span class="term" data-tip="측정값을 작은 순서로 놓았을 때 95%가 이 값 이하에 들어오는 백분위. 응답 시간 P95가 3초라면 요청의 약 5%는 3초보다 느렸다는 뜻이다.">P95</span> 응답 시간 | 8.7초 |
| 일 평균 Claude <span class="term" data-tip="소프트웨어가 다른 소프트웨어의 기능이나 데이터에 접근할 때 따르는 호출 계약. 사용할 주소, 입력 형식, 인증, 응답과 오류 규칙을 함께 정의한다.">API</span> 비용 | $1.24 |
| 전체 메시지 중 단순 Q&A | ~63% |

눈에 띈 건 단순 Q&A 비율이었다. 63%가 "오늘 뭐야?", "어떤 게 뭐야?" 같은 짧은 질문인데, 이걸 전부 Claude Sonnet이 받고 있었다.

## 개선 1: 멀티 모델 라우팅

요청을 세 가지 작업 유형으로 나누고 유형마다 다른 모델로 보냈다.

```
FAST_QA  → Gemini Flash 2.0   (응답 시간: ~1.2초, 비용: ~$0.0001/건)
TOOL_TASK → Claude Sonnet 4.5  (응답 시간: ~4.5초, 비용: ~$0.02/건)
DEEP_TASK → Claude Sonnet 4.5  (응답 시간: ~15~40초, 비용: ~$0.10/건)
```

분류기는 키워드 기반으로 만들었다. ML 분류기를 따로 두지 않은 데는 이유가 있다.

1. 분류하느라 레이턴시가 늘면 라우팅하는 의미가 없다.
2. 도메인이 좁다. 캘린더, GitHub, Notion, GCS 키워드가 분명하게 갈린다.
3. 잘못 분류할 거라면 TOOL_TASK 쪽으로 넘치는 편이 FAST_QA로 빠지는 것보다 낫다.

개선 후 2주(n=312)의 실제 분류 결과는 이랬다.

| 분류 | 비율 | 오분류율 |
|------|------|---------|
| FAST_QA | 65% | ~3% (도구가 필요했는데 빠진 경우) |
| TOOL_TASK | 32% | ~1% |
| DEEP_TASK | 3% | ~0% |

## 개선 2: 프롬프트 캐싱

Claude API의 프롬프트 캐싱을 켰다.

캐싱 대상은 <span class="term" data-tip="대화 전체에 적용할 역할·행동 규칙·출력 제약을 모델에 전달하는 상위 지시. 공급자 API에 따라 system 또는 developer 메시지로 표현된다.">시스템 프롬프트</span>(~2,400 tokens)와 tools 정의(~1,800 tokens)다. 설정은 `cache_control: { type: "ephemeral" }`이고 <span class="term" data-tip="Time To Live. 데이터에 걸어 두는 유효 시간으로, 지나면 자동 삭제된다. 진행률처럼 잠깐만 의미 있는 값을 별도 청소 코드 없이 관리할 수 있다.">TTL</span>은 5분이다.

캐시 히트가 나면 읽기 기준으로 토큰당 비용이 90% 줄고, 레이턴시도 50% 안팎 줄어든다.[^1]

실제 <span class="term" data-tip="캐시 조회 또는 재사용 대상 중 실제 캐시에서 처리된 비율. 토큰·블록·요청 중 무엇을 분모로 삼는지는 구현마다 달라 같은 이름의 수치를 바로 비교하면 안 된다.">캐시 히트율</span>은 대화가 몰리는 시간대 기준으로 약 72%였다. 5분 넘게 대화가 없으면 캐시가 만료되니, 효과는 쓰는 패턴에 따라 달라진다.

## 한계와 트레이드오프

사용 패턴이 바뀌면 이 수치도 그대로 유지되지 않는다.

### FAST_QA 오분류

"이슈 뭐야?"는 TOOL_TASK로 가야 하는 질문이다. 이게 FAST_QA로 빠지면 Gemini가 "어떤 이슈를 말씀하시나요?" 같은 애매한 답을 준다. 사용자가 다시 물어야 하니 전체 시간은 오히려 늘어난다.

### 캐시 미스

5분 넘게 조용하다가 새 메시지가 오면 캐시가 비어 있다. 첫 메시지에는 늘 캐싱 비용이 붙고, 봇을 자주 쓰지 않는 날은 아끼는 금액도 작다.

### Gemini와 Claude의 답 품질 차이

FAST_QA로 분류된 질문이라도 미묘한 맥락이 필요하면 Gemini가 더 얕게 답할 때가 있다. 이 문제는 아직 풀지 못했다.

## 다음 최적화 방향

지금 P95 3.1초를 끌어올리는 건 대부분 TOOL_TASK다. GitHub API나 Google Calendar API 호출만으로 0.5~1.5초가 나간다. 모델을 바꿔서는 줄일 수 없는 시간이다.

그래서 다음으로 병렬 도구 호출을 보고 있다. `asyncio.gather`로 일부는 이미 구현해 뒀고, 서로 의존하지 않는 도구를 동시에 돌리면 P95를 더 줄일 수 있을 것 같다.
