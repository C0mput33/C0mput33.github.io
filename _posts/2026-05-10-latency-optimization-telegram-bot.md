개인용 Telegram 봇의 평균 응답 시간은 4.2초, P95는 8.7초였습니다. 7일간 쌓인 기준선 로그 218건을 확인한 뒤 멀티 모델 <span class="term" data-tip="들어온 요청을 여러 서버·모델·공급자 후보 중 하나로 보내는 선택 과정. 가용성, 현재 부하, 비용, 캐시 재사용 가능성처럼 목적에 맞는 기준과 실패 시 대체 경로가 필요하다.">라우팅</span>과 <span class="term" data-tip="반복되는 프롬프트 앞부분의 계산 결과를 재사용해 지연이나 입력 비용을 줄이는 기능. 자동·명시형 여부, 최소 길이, 만료 시간, 할인율은 모델과 공급자마다 다르다.">프롬프트 캐싱</span>을 적용했고, 이후 2주 로그에서 평균 1.8초, P95 3.1초로 줄었습니다.

아래에서는 측정 조건과 두 변경이 각각 맡은 역할을 정리했습니다. 아직 남아 있는 오분류와 <span class="term" data-tip="요청한 데이터나 프롬프트 상태가 캐시에 없어 원래 계산이나 저장소 조회를 다시 수행하는 경우. 캐시 키·만료·라우팅이 달라져도 발생할 수 있다.">캐시 미스</span> 문제도 함께 적었습니다.

## 1. 문제 상황

개선 전 7일간의 메시지 로그(n=218)를 분석했습니다. 기준선은 다음과 같습니다.

| 지표 | 값 |
|------|-----|
| 평균 응답 시간 | 4.2초 |
| <span class="term" data-tip="측정값을 작은 순서로 놓았을 때 95%가 이 값 이하에 들어오는 백분위. 응답 시간 P95가 3초라면 요청의 약 5%는 3초보다 느렸다는 뜻이다.">P95</span> 응답 시간 | 8.7초 |
| 일 평균 Claude <span class="term" data-tip="소프트웨어가 다른 소프트웨어의 기능이나 데이터에 접근할 때 따르는 호출 계약. 사용할 주소, 입력 형식, 인증, 응답과 오류 규칙을 함께 정의한다.">API</span> 비용 | $1.24 |
| 전체 메시지 중 단순 Q&A | ~63% |

눈에 띈 건 단순 Q&A 비율이었습니다. 전체의 63%가 "오늘 뭐야?", "어떤 게 뭐야?" 같은 짧은 질문이었는데, 이 질문까지 모두 Claude Sonnet이 처리하고 있었습니다.

## 2. 개선 방법

### 2-1. 작업 유형별 모델 라우팅

요청을 세 가지 작업 유형으로 나누고, 유형마다 다른 모델로 보내도록 바꿨습니다. 유형별 구성은 다음과 같습니다.

| 작업 유형 | 모델 | 응답 시간 | 비용 |
|---|---|---|---|
| FAST_QA | Gemini Flash 2.0 | 약 1.2초 | 건당 약 $0.0001 |
| TOOL_TASK | Claude Sonnet 4.5 | 약 4.5초 | 건당 약 $0.02 |
| DEEP_TASK | Claude Sonnet 4.5 | 약 15~40초 | 건당 약 $0.10 |

분류기는 키워드 기반으로 구현했습니다. 별도 ML 분류기를 두지 않은 이유는 세 가지입니다.

1. 분류 자체에 레이턴시가 더해지면 라우팅하는 의미가 없습니다.
2. 도메인이 좁습니다. 캘린더, GitHub, Notion, GCS 키워드가 분명하게 갈립니다.
3. 틀리더라도 FAST_QA로 잘못 빠지는 것보다 TOOL_TASK로 넘치는 편이 낫습니다.

개선 후 2주(n=312) 동안의 실제 분류 결과는 다음과 같습니다.

| 분류 | 비율 | 오분류율 |
|------|------|---------|
| FAST_QA | 65% | ~3% (도구가 필요했는데 빠진 경우) |
| TOOL_TASK | 32% | ~1% |
| DEEP_TASK | 3% | ~0% |

전체 요청의 65%가 FAST_QA로 분류되어 Gemini Flash로 넘어갔습니다.

### 2-2. 프롬프트 캐싱

<span class="term" data-tip="대화 전체에 적용할 역할·행동 규칙·출력 제약을 모델에 전달하는 상위 지시. 공급자 API에 따라 system 또는 developer 메시지로 표현된다.">시스템 프롬프트</span>(~2,400 tokens)와 tools 정의(~1,800 tokens)는 매 요청에 똑같이 붙습니다. 그래서 Claude API의 프롬프트 캐싱을 켜고 이 두 부분을 캐싱 대상으로 지정했습니다. 설정은 `cache_control: { type: "ephemeral" }`이고 <span class="term" data-tip="Time To Live. 데이터에 걸어 두는 유효 시간으로, 지나면 자동 삭제된다. 진행률처럼 잠깐만 의미 있는 값을 별도 청소 코드 없이 관리할 수 있다.">TTL</span>은 5분입니다.

캐시 히트가 나면 읽기 기준으로 토큰당 비용이 90% 줄고, 레이턴시도 50% 안팎 줄어듭니다.[^1]

실제로 측정해보니 대화가 몰리는 시간대의 <span class="term" data-tip="캐시 조회 또는 재사용 대상 중 실제 캐시에서 처리된 비율. 토큰·블록·요청 중 무엇을 분모로 삼는지는 구현마다 달라 같은 이름의 수치를 바로 비교하면 안 된다.">캐시 히트율</span>은 약 72%였습니다. 5분 이상 대화가 없으면 캐시가 만료되기 때문에, 사용 패턴에 따라 효과가 달라집니다.

## 3. 결과

두 변경을 적용한 전후 비교는 다음과 같습니다.

| 지표 | 개선 전 | 개선 후 | 변화 |
|------|---------|---------|------|
| 평균 응답 시간 | 4.2초 | 1.8초 | -57% |
| P95 응답 시간 | 8.7초 | 3.1초 | -64% |
| 일 평균 API 비용 | $1.24 | $0.35 | -72% |

측정 기간은 개선 전 7일(n=218), 개선 후 2주(n=312)입니다. 두 기간의 사용 패턴은 같았습니다. 사용 패턴이 바뀌면 이 수치도 그대로 유지되지 않습니다.

## 4. 남은 문제

### 4-1. FAST_QA 오분류

"이슈 뭐야?"는 TOOL_TASK로 가야 하는 질문입니다. 이 질문이 FAST_QA로 빠지면 Gemini가 "어떤 이슈를 말씀하시나요?"라고 되묻습니다. 그러면 다시 질문해야 해서 전체 시간은 오히려 늘어납니다.

### 4-2. 캐시 미스

5분 넘게 대화가 없다가 새 메시지가 오면 캐시 미스가 납니다. 첫 메시지에는 항상 캐싱 비용이 붙습니다. 봇을 자주 쓰지 않는 날은 절감 효과도 작습니다.

### 4-3. Gemini와 Claude의 응답 품질 차이

FAST_QA로 분류된 질문이라도 미묘한 맥락이 필요하면 Gemini가 더 피상적으로 답할 때가 있습니다. 이 문제는 아직 해결하지 못했습니다.

## 마치며

질문 유형별로 모델을 나누고 반복되는 프롬프트를 캐싱해서 평균 응답 시간을 4.2초에서 1.8초로, 일 평균 API 비용을 $1.24에서 $0.35로 줄였습니다.

지금 P95 3.1초의 대부분은 TOOL_TASK가 차지합니다. GitHub API나 Google Calendar API 호출에만 0.5~1.5초가 걸리는데, 이 부분은 모델을 바꿔도 줄어들지 않습니다. 다음 단계로는 병렬 도구 호출을 검토하고 있습니다. 일부는 이미 `asyncio.gather`로 구현해 두었고, 서로 독립적인 도구를 동시에 실행하면 P95를 더 줄일 수 있을 것으로 보고 있습니다.
