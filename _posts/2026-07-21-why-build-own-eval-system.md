이 시리즈를 쓰는 동안 가장 많이 받은 질문은 공개 벤치마크가 이미 많은데 왜 평가 시스템을 직접 만들었느냐는 것이었습니다. <span class="term" data-tip="57개 과목의 객관식 문제로 언어 모델의 지식과 문제 해결 능력을 평가하는 벤치마크. 실제 제품의 창작 품질이나 연령 적합성을 직접 재는 시험은 아니다.">MMLU</span> 점수도, 창작 리더보드도, 아레나 순위도 모두 공개돼 있습니다. 제가 쓰는 모델도 품질이 좋은 기성 <span class="term" data-tip="소프트웨어가 다른 소프트웨어의 기능이나 데이터에 접근할 때 따르는 호출 계약. 사용할 주소, 입력 형식, 인증, 응답과 오류 규칙을 함께 정의한다.">API</span> 모델입니다. 그런데도 평가 시스템을 만드는 데 한 달을 썼습니다.

이유는 세 가지였습니다. 공개 벤치마크는 이 프로젝트에서 재야 하는 항목을 재지 않았습니다. 빌려 쓰는 모델은 예고 없이 바뀌거나 사라집니다. 그리고 모델을 직접 학습하려면, 나아졌는지 잴 기준이 학습보다 먼저 있어야 했습니다. 아래에서는 이 세 가지를 프로젝트에서 실제로 부딪힌 문제와 비용 계산을 근거로 정리했습니다.

## 1. 동화 평가에서 재야 하는 것

제가 다루는 것은 아동용 영어 동화를 생성하는 모델입니다. 좋은 동화를 판단하는 기준은 일반 텍스트 품질과 잘 겹치지 않습니다. 독자 연령에 맞는 어휘와 문장 난이도(<span class="term" data-tip="영어 독자의 읽기 능력과 텍스트 난이도를 같은 척도에 표시하는 상용 지표. 텍스트 측정은 어휘의 빈도와 문장 길이 같은 특성을 사용하며, 이 프로젝트의 가독성 공식 합성값은 공인 Lexile이 아니다.">Lexile</span>), 연령 적합성, 안전성, 그리고 뻔하지 않은 이야기가 필요합니다. 일반 벤치마크의 채점 기준에는 이런 항목이 없습니다.

관련 연구는 있었습니다. KidLM은 <span class="term" data-tip="Large Language Model. 많은 텍스트에서 토큰의 조건부 분포를 학습해 문장을 생성하거나 분류·요약·추론 작업을 수행하는 언어 모델을 뜻한다.">LLM</span>이 아동 특화 언어, 인지 단계, 안전 기준을 지키는 데 아직 과제가 남아 있다고 지적합니다.[^kidlm]
MinorBench는 6개 LLM의 아동 안전 준수가 모델과 설정마다 달랐다고 보고합니다.[^minorbench]
다만 아동용 창작 품질을 직접 재는 공개 벤치마크는 제가 조사한 범위에서는 찾지 못했습니다.

## 2. 공개 벤치마크의 한계

도메인 기준이 없다는 점 외에도, 공개 벤치마크를 순위 근거로 쓰기 어려운 이유가 세 가지 더 있었습니다.

### 2-1. 포화

MMLU-Pro 논문에 따르면 2023년 3월 GPT-4가 MMLU에서 86.4%를 기록한 뒤로 의미 있는 진전이 없었습니다. 2024년 프론티어 모델들은 모두 86~87% 구간에 몰렸습니다. 다른 벤치마크에서 10%p 넘게 오른 모델도 MMLU에서는 1%p 올랐습니다.[^mmlupro] 상위권이 천장에 붙으면 그 벤치마크로는 상위권끼리 비교할 수 없습니다.

창작 평가도 같은 문제를 겪었습니다. eqbench.com은 창작 평가 v2가 포화돼 심판이 최상위권 모델을 더 이상 구별하지 못했다고 밝혔습니다. 그래서 v3에서는 절대 점수 대신 쌍대 비교로 바꿨습니다.[^eqbench]

### 2-2. 오염

공개 문제가 학습 데이터에 섞이면 점수에 암기가 반영될 수 있습니다.[^cheater]
<span class="term" data-tip="초등학교 수준의 다단계 수학 서술형 문제 8,500개로 구성된 벤치마크. 모델이 답만 맞히는지보다 여러 계산 단계를 이어갈 수 있는지를 평가한다.">GSM8K</span>와 난이도를 맞춘 GSM1k로 다시 평가하자 주요 모델의 정확도가 최대 8%p 떨어졌고, 일부 계열에서는 과적합 증거가 나왔습니다.[^gsm1k]
비공개로 새로 만든 프롬프트를 쓰면 알려진 공개 문항을 암기했을 위험은 줄어듭니다. 하지만 비슷한 문항에 노출됐을 가능성까지 없애지는 못합니다.

### 2-3. 순위가 다른 과제로 옮겨 가지 않는 문제

40여 개 벤치마크를 비교한 연구는 벤치마크끼리 결과가 어긋나고, 분석 방법에 따라 결론이 바뀐다고 보고했습니다.[^benchbench] <span class="term" data-tip="사용자가 익명화된 두 모델 응답을 비교해 투표하는 공개 평가 플랫폼의 초기 이름. 현재 LMArena는 대규모 사람 선호 데이터를 Bradley–Terry 계열 모델로 집계한다.">Chatbot Arena</span>에서도 전체 순위 상위권 모델이 어려운 프롬프트 범주에서는 순위가 내려간 사례가 있습니다.[^hardprompts]

제 실측에서도 비슷한 신호가 있었습니다. 레거시 런이긴 하지만, 같은 회사 모델인 Opus 4.8이 4.7보다 낮게 나왔습니다.[^ourrun] 쌍-군집 주변 <span class="term" data-tip="Confidence Interval의 약칭. 이 글에서는 추정 불확실성을 나타내는 신뢰구간을 뜻하며 CI/CD의 CI와는 다른 용어다.">CI</span>는 겹치지 않았습니다. 다만 프롬프트-군집 참고 구간은 겹쳤고, 프롬프트 13개와 적응형 은퇴 경로를 거친 결과라는 조건도 붙습니다. 그래서 범용 순위가 도메인 순위로 그대로 옮겨지지 않을 수 있다는 가설로만 두고, 다시 검증할 계획입니다.

## 3. 기성 API 모델의 통제 문제

지금 쓰는 프론티어 모델은 글을 잘 씁니다. 제가 걸린 부분은 품질이 아니라 통제였습니다.

빌려 쓰는 모델은 바뀝니다. 스탠퍼드·버클리 연구진이 같은 GPT-4의 2023년 3월판과 6월판을 비교한 결과, 행동이 크게 달랐습니다. 소수/합성수 판별 정확도는 84%에서 51%로 떨어졌습니다.[^drift]

모델이 아예 사라지기도 합니다. OpenAI는 정식 모델을 최소 6개월 전에 알리고 종료하는 단종 정책을 두고 있습니다. Anthropic은 최소 60일 전에 알린 뒤 모델을 은퇴시키고, 은퇴한 모델로 보낸 요청은 실패한다고 명시합니다.[^deprecation] 어떤 모델을 고르든 언젠가는 교체해야 합니다.

교체할 때마다 우리 도메인에서 나아졌는지 나빠졌는지를 감으로 정하고 싶지는 않았습니다. 자체 평가가 있으면 교체를 판정으로 결정할 수 있습니다. 비용도 마찬가지입니다. 나중에 측정해보니 같은 동화 한 권의 생성 원가가 모델에 따라 240배까지 차이 났습니다.[^cost] 더 싼 모델로 바꿔도 되는지는 가격표만으로 알 수 없고, 품질을 재 봐야 알 수 있습니다.

## 4. 자체 모델의 보안과 비용 검토

여기까지 정리하고 보니 빠진 설명이 하나 있었습니다. 자체 모델을 왜 학습하고 운영하려 하는지입니다. 보통 보안과 비용을 이유로 드는데, 둘 다 배포 방식만 바꾼다고 저절로 얻어지지는 않습니다.

### 4-1. 데이터 보안

Anthropic의 상용 API는 고객 입력과 출력을 기본적으로 학습에 쓰지 않습니다. 표준 API 입력·출력은 예외 조건이 없으면 30일 안에 삭제한다고 밝히고 있습니다. <span class="term" data-tip="여러 회사의 LLM을 하나의 API와 결제로 호출하게 해주는 중계 서비스. 모델마다 계정을 따로 만들 필요가 없어 다모델 비교 실험에 편하다.">OpenRouter</span>도 프롬프트·응답 로깅이 기본으로 꺼져 있고, 요청별로 데이터를 보존하지 않는 공급자만 쓰도록 설정할 수 있습니다.[^privacy] “외부 API에 보내면 바로 학습 데이터가 된다”는 말은 사실과 다릅니다.

로컬에서 실행하면 믿어야 할 외부 사업자가 줄고, 데이터 경계를 직접 정할 수 있습니다. 입력이 맥북 밖으로 나가지 않게 구성할 수 있고, AWS에 직접 올리면 계정·리전·네트워크·로그 정책도 고를 수 있습니다. 대신 디스크 암호화, 접근 권한, 로그 삭제, 운영체제와 컨테이너 패치를 모두 직접 책임져야 합니다. AWS도 <span class="term" data-tip="AWS에서 가상 서버를 직접 빌려 운영하는 서비스. GPU 인스턴스에 모델 서버를 올리면 런타임과 네트워크를 세밀하게 제어할 수 있지만 시작·보안·모니터링·축소를 직접 책임져야 한다.">EC2</span>의 게스트 운영체제, 애플리케이션, 보안 그룹, 데이터 보호는 고객 책임이라고 명시합니다.[^shared]

지금 쓰는 합성 평가 프롬프트에는 민감한 사용자 데이터가 없습니다. 따라서 보안만으로 Opus를 버릴 이유는 아직 없습니다. 데이터 통제가 자체 모델의 근거가 되는 시점은, 실제 서비스가 아동 맞춤 입력처럼 외부로 보내기 어려운 데이터를 다루고, API의 보존 기간이나 리전, 계약 조건으로 그 요구를 맞추지 못할 때입니다.

### 4-2. Opus 4.8과 Qwen3.6 비용 비교

가격표 기준으로 Opus 4.8 표준 API는 입력 100만 토큰당 $5, 출력 100만 토큰당 $25입니다. 캐시 읽기는 더 싸고 배치는 표준 단가의 절반이라, 실제 비용은 입력 길이와 반복 구조에 따라 달라집니다.[^opusprice] 그래서 가격표 대신 2026년 7월 19일에 같은 25페이지 생성 프롬프트를 모델마다 5회 돌린 <span class="term" data-tip="오픈라우터가 모든 응답의 usage 객체에 실어주는 실제 청구 금액(usage.cost). 토큰 수에 단가를 곱해 추정하는 것이 아니라 계정에서 실제로 빠져나간 크레딧이다.">실청구액</span>을 기준선으로 잡았습니다.[^cost25]

단순 <span class="term" data-tip="두 선택지의 총비용이 같아지는 지점. 여기서는 GPU 월 고정비를 관리형 API의 권당 변동비로 나눠 몇 권부터 GPU가 싸지는지를 계산한다. 대체 대상이 쌀수록 분기점은 뒤로 밀린다.">손익분기</span>는 Opus 대비 월 약 24,015권, 호스팅 Qwen 대비 월 약 55,351권입니다. 저장, 전송, 모니터링, 실패 재시도, 운영 인건비를 더하면 손익분기는 더 뒤로 밀립니다. GPU 한 장이 그 물량을 감당할 수 있는지도 별개 문제입니다. 월 24,015권이면 730시간 내내 시간당 약 33권을, 월 55,351권이면 약 76권을 성공시켜야 합니다.

EC2를 항상 켜 두지 않고 작업이 있을 때만 켜면 계산이 달라집니다. 다른 비용을 모두 빼고 한 번에 한 권씩 만든다고 가정해보겠습니다. 권당 GPU 활성 시간이 약 110초보다 짧아야 Opus $0.06993보다 쌉니다. 호스팅 Qwen $0.03034보다 싸려면 약 47.7초 이하여야 합니다. 우리 프롬프트를 <span class="term" data-tip="NVIDIA의 서빙·그래픽 겸용 GPU로 VRAM 48GB. 모델 가중치와 KV 캐시가 VRAM에 다 들어가야 서빙이 성립하므로, 24GB(L4)냐 48GB(L40S)냐가 올릴 수 있는 모델의 상한을 가른다.">L40S</span>에서 측정한 적은 아직 없습니다. 이 숫자들은 다음 실험에서 넘어야 할 기준선으로 적어 두었습니다.

### 4-4. 맥북 로컬 실행 비용

맥북 비용은 판단이 애매했습니다. 이미 샀으니 공짜라고 보기도, 구매가 전체를 모델 비용으로 치기도 어렵습니다. 업무용으로 이미 가진 장비라 구매가는 이번 결정으로 되돌릴 수 없는 비용입니다. 추가로 드는 비용은 전력과 장비 점유 시간에 가깝습니다.

전기료는 `평균 벽전력(kW) × 실행시간(h) × kWh 요금`으로 계산합니다. 평균 100W, $0.15/kWh로 가정하면 1분에 $0.00025, 10분에 $0.0025입니다. 감을 잡기 위한 민감도 예시이고 실측값은 아닙니다. 실제 벽전력, 생성시간, 발열, 배터리 영향, 운영에 쓰는 시간까지 측정하기 전에는 로컬 총원가를 확정할 수 없습니다.

## 5. 비용 외에 자체 모델을 검토하는 이유

Qwen3.6-35B-A3B는 약 35B 전체 가중치 중 <span class="term" data-tip="모델의 토크나이저가 텍스트를 나눈 처리 단위. 한 토큰은 단어 하나와 같지 않으며 같은 문장도 모델별 토크나이저에 따라 토큰 수가 달라질 수 있다.">토큰</span>마다 약 3B만 활성화하는 모델이고, Apache 2.0으로 가중치가 공개돼 있습니다.[^qwen36] <span class="term" data-tip="모델 이름에서 토큰 하나를 처리할 때 활성화되는 파라미터가 약 3B라는 표기. 총 파라미터와 상주 메모리 크기는 별도라서 A3B만 보고 3B 모델처럼 적재할 수는 없다.">A3B</span>라고 해서 3B 모델만큼 가볍지는 않습니다. 그래도 기성 API로는 얻기 어려운 제어권이 있었습니다.

첫째는 가중치를 직접 다룰 수 있다는 점입니다. 같은 베이스 리비전에 <span class="term" data-tip="원본 가중치는 얼려 두고 곁에 붙인 작은 저랭크 행렬(어댑터)만 학습하는 파인튜닝 기법. 학습 대상이 전체의 1% 미만이라 메모리와 시간이 크게 줄고, 어댑터만 따로 저장·교체할 수 있다.">LoRA</span> <span class="term" data-tip="동결한 베이스 모델 옆에 붙여 학습하는 작은 추가 가중치 묶음. 파일이 작아도 층 이름과 배열 모양이 실행 프레임워크의 형식과 맞지 않으면 그대로 옮겨 쓸 수 없다.">어댑터</span>를 붙여 아동용 문체와 출력 계약을 실험해볼 수 있습니다. 기성 API에는 우리 가중치를 올릴 방법이 없습니다. 모델 파일, 토크나이저, 어댑터 리비전을 한 묶음으로 고정하면 공급자가 모델을 바꾸거나 은퇴시키는 일정에도 영향을 받지 않습니다. 물론 런타임과 보안 패치는 계속 관리해야 합니다.

둘째는 실행 경로를 직접 정할 수 있다는 점입니다. 사고 모드, 최대 토큰, <span class="term" data-tip="가중치나 활성값을 더 적은 비트로 근사해 메모리와 연산량을 줄이는 기법. 절감 폭과 품질 손실은 양자화 방식·비트 수·하드웨어에 따라 달라지며 Q4 같은 이름도 포맷별 세부 규칙을 확인해야 한다.">양자화</span>, 배칭, 캐시, 거절·재시도, 로그 범위를 제품 조건에 맞출 수 있습니다. 로컬에서는 API 과금 없이 같은 입력을 반복해서 돌릴 수 있어서, 파인튜닝 전후 회귀 검사나 디버깅처럼 호출이 많은 작업에 유리합니다. 외부 API 장애나 <span class="term" data-tip="클라우드·API가 계정별로 거는 사용 한도(분당 요청 수 RPM, 분당 토큰 TPM 등). 돈을 낼 수 있어도 쿼터가 없으면 호출 자체가 거부되므로 용량 계획에서 가장 먼저 확인할 항목이다.">쿼터</span> 부족 때 기능 일부를 유지할 후보도 됩니다. 다만 자체 서버 장애를 새로 떠안는 것이라 가용성이 저절로 올라가지는 않습니다.

개발 경험도 이유가 될 수는 있습니다. 모델 서버, <span class="term" data-tip="작업 완료를 기다리며 실행 흐름 전체를 막지 않고, 결과를 나중에 받도록 분리하는 방식. 비동기라고 해서 자동으로 병렬 실행되거나 더 빨라지는 것은 아니다.">비동기</span> 작업 큐, 관측, 장애 복구를 직접 구현해보는 경험은 포트폴리오에 도움이 됩니다. 하지만 제품 근거와는 섞지 않았습니다. 서비스가 감당할 운영 비용보다 개인이 배우는 것이 더 크다고 말할 수는 없기 때문입니다.

현재는 두 경로를 함께 쓰고 있습니다. Opus는 고품질 기준선이자 복잡한 요청의 대체 경로로 남겨 두고, Qwen은 로컬 추론과 LoRA 실험, AWS 스모크를 차례로 거치게 했습니다. Qwen을 기본 생성 경로로 올리는 조건은 새 평가에서 미리 정한 품질 허용폭, 유효 응답률, 지연, 권당 총원가를 모두 통과하는 것입니다. 평가 시스템을 먼저 만든 이유 중 하나도 이 교체를 가격이나 인상으로 결정하지 않기 위해서였습니다.

실제로 측정하려면 Little Bard에서 `local-qwen-base`와 `local-qwen-childlit-lora-v1`을 서로 다른 모델 ID로 호출해야 합니다. 베이스·토크나이저 리비전과 어댑터 체크섬도 결과에 함께 남깁니다. 로컬 연결이 실패하거나 모델이 잘못 로드된 경우에는 무승부로 바꾸지 않고 생성 `invalid`로 제외합니다.

지금 <span class="term" data-tip="Python 함수와 모델 데모를 웹 UI로 감싸고, 연결된 이벤트 함수의 호출 문서를 자동 생성하는 오픈소스 도구. 자동 API 노출은 개발 편의 기능이며 인증이나 네트워크 보안 자체를 대신하지 않는다.">Gradio</span> 화면은 모델 적재와 단일 출력만 확인하는 개발 스모크입니다.
평가 HTML에는 기존 <span class="term" data-tip="오픈 웨이트 모델을 로컬 장비에서 내려받아 실행하고 API로 호출하게 해주는 도구. 외부 모델 API의 호출 요금은 없지만 장비·전력·운영 비용은 별도다.">Ollama</span> 공급자 경계를 OpenAI 호환 로컬 어댑터로 일반화해서 붙일 계획입니다.

## 6. 학습 전에 평가 기준이 필요한 이유

텍스트 모델을 먼저 보는 이유는 이 서비스의 핵심이 텍스트에 있기 때문입니다. 아이마다 다른 수준에 맞춰 난이도를 조절한 이야기를 쓰는 것이 핵심이고, 난이도 조절은 텍스트에서만 생기는 문제입니다. 삽화는 기성 이미지 모델로도 충분히 잘 그립니다. 차별화할 지점과 어려운 문제가 모두 텍스트 쪽에 있었습니다.

자체 모델로 개선하고 싶은 것도 앞에서 말한 기준들입니다. 난이도 적합, 안전성, 이야기 품질을 우리 데이터로 끌어올리는 것이 목표입니다. 그러려면 이를 재는 기준이 학습보다 먼저 있어야 합니다. 학습 전후 점수를 같은 기준으로 재고 그 차이에 신뢰구간을 붙이지 못하면, <span class="term" data-tip="사전학습된 모델을 특정 데이터와 목적에 맞게 추가 학습하는 과정. 전체 가중치를 바꾸는 방식과 LoRA처럼 일부만 학습하는 방식은 메모리·이식성이 다르다.">파인튜닝</span>으로 나아졌는지 나빠졌는지 판단할 수 없습니다.

생성물 몇 개를 눈으로 보면 되지 않느냐는 질문도 있었습니다. 답은 나중에 쌓인 실측에서 나왔습니다. 우리 리그에서 5위(1050)와 4위(1052)는 신뢰구간이 겹쳤습니다.[^ourrun] 이 정도 차이는 몇 개를 읽어 보고 받은 인상으로는 가릴 수 없습니다. 개선폭이 이 구간 안에 있으면 통계 없이는 결론을 낼 수 없습니다.

## 7. 평가 시스템 구성

평가 시스템은 세 부분으로 구성했습니다. 두 동화를 나란히 놓는 쌍대 비교, 그 승패를 <span class="term" data-tip="맞대결 승패만으로 각 후보의 숨은 실력을 추정하는 통계 모델(1952). 실력 차가 승률을 정한다고 가정하고, 관측된 모든 승패를 가장 잘 설명하는 실력값을 최우도로 찾는다. 경기 순서와 무관하게 같은 답이 나오는 배치 방식이라, 고정된 대전 기록의 순위에 적합하다.">Bradley-Terry</span>로 집계한 순위, 불확실성을 보여 주는 <span class="term" data-tip="가진 데이터에서 복원추출로 여러 번 가짜 표본을 만들어 같은 계산을 반복하고, 그 결과들의 흩어짐으로 추정치의 불확실성을 재는 방법. 표본이 모집단을 대표한다면 재표집의 흔들림이 실제 추정 오차와 비슷하다는 원리다.">부트스트랩</span> <span class="term" data-tip="같은 절차로 표본을 반복 수집할 때 정해진 비율만큼 모수를 포함하도록 만든 구간. 두 개의 95% 신뢰구간이 겹치는지만으로 차이의 유의성을 판정할 수는 없다.">신뢰구간</span>입니다. 심판 편향은 평가 순서와 심판 계열을 나눠 줄이고, 남은 오차는 소량의 사람 평가로 확인합니다. 창작 평가가 포화된 뒤 쌍대 비교로 옮겨 간 사례가 있었고,[^eqbench] Chatbot Arena도 순위 안정성과 신뢰구간 때문에 2023년 12월 <span class="term" data-tip="경기가 끝날 때마다 결과와 기대승률의 차이만큼 점수를 즉시 조정하는 체스식 레이팅. 실력이 변하는 선수를 추적하는 데 좋지만, 경기 순서에 따라 최종 값이 달라져 고정된 대전 기록의 순위에는 부적합하다.">Elo</span>에서 Bradley-Terry로 바꿨습니다.[^arena-bt]

각 선택의 이유는 [2편](/posts/llm-eval-pipeline-from-scratch-bradley-terry/)부터 차례로 정리했습니다. 방법 선택(2편), 단일 <span class="term" data-tip="웹 문서의 구조와 의미를 요소로 표시하는 마크업 언어. CSS는 표현을, JavaScript는 동작을 주로 담당한다.">HTML</span> 앱(3편), 스케줄러(4편), $46.76 실측(5편), <span class="term" data-tip="변경을 만든 쪽과 검토하는 쪽이 같은 대화 맥락을 공유하지 않게 분리하는 검토 방식. 검토자는 변경 내역과 검증 기준만 보고 판단한다.">교차 리뷰</span>로 찾은 결함(6편), 신뢰구간 교정(7편), <span class="term" data-tip="사람이 직접 평가한 소량의 기준 데이터. 같은 항목을 자동(LLM) 평가와 사람이 모두 평가하게 한 뒤 일치도를 재면, 자동 평가를 얼마나 믿어도 되는지가 숫자로 나온다.">골든셋</span>과 데이터 유실(8편) 순서입니다.

## 8. LLM 심판을 쓰는 근거와 한계

더 근본적인 질문이 하나 남습니다. 생성 모델이 쓴 글을 왜 또 다른 생성 모델에게 채점시키느냐는 것입니다. 같은 종류끼리 평가하면 그럴듯한 오류가 반복되지 않을까 하는 우려입니다.

### 8-1. 역할 분담

동화에는 정답 문자열이 없습니다. 단어 수와 출력 형식은 코드로 확인할 수 있습니다. 하지만 어느 쪽이 더 자연스럽고 재미있는지, 아이가 따라가기 쉬운지는 문자열 일치율이나 <span class="term" data-tip="글을 얼마나 수월하게 읽고 이해할 수 있는지를 뜻한다. 문장·단어 표면값으로 계산한 가독성 공식은 정량 단서일 뿐 의미 구조, 배경지식, 독자와 읽기 목적 전체를 대신하지 않는다.">가독성</span> 공식으로 판단할 수 없습니다. 기준은 사람 평가인데, 문제는 양입니다. 모델 13개, 프롬프트 수십 개, 정·역방향, 여러 평가자를 곱하면 사람이 읽어야 할 본문이 금방 수천 건이 됩니다. 모두 사람에게 맡기면 비용도 들지만 평가자가 지치고 기준도 흔들립니다.

그래서 <span class="term" data-tip="사람 대신 LLM에게 후보 응답을 비교하거나 점수화하게 하는 평가 방식. 빠르게 확장할 수 있지만 위치·길이·자기 선호 같은 편향을 별도로 통제하고 사람 기준과 대조해야 한다.">LLM-as-a-Judge</span>를 적용했습니다. 사람을 빼려는 목적은 아닙니다. 의미를 읽어야 하는 대량 비교를 먼저 걸러서, 사람이 볼 표본과 애매한 사례를 줄이려는 목적입니다. 역할은 다음과 같이 나눴습니다.

| 판단 대상 | 맡기는 방법 | 이유 |
|---|---|---|
| 빈 출력, 단어 수, 금지 형식처럼 기계적으로 확인 가능한 조건 | 코드 검사 | 같은 입력에는 같은 답이 나오며 LLM의 해석이 필요 없다 |
| 이야기 진행, 자연스러움, 정서적 울림처럼 정답이 하나가 아닌 품질 | 익명화한 LLM <span class="term" data-tip="후보를 둘씩 제시하고 어느 쪽을 선호하는지 기록하는 비교 방식. 절대 점수보다 판단 부담을 줄일 수 있지만 순서 효과와 평가자 편향은 별도로 통제해야 한다.">pairwise</span> 판정 | 여러 유효한 답을 의미 수준에서 비교할 수 있다 |
| 심판의 기준이 실제 독자·팀의 판단과 맞는지 | 사람 골든셋 | 자동 심판의 타당도는 같은 도메인의 사람 판정으로 확인해야 한다 |
| 안전 경계, 심판 불일치, 근소한 교체 결정 | 사람에게 재검토 | 자동화의 불확실성이 큰 사례를 그대로 확정하지 않는다 |

### 8-2. 선행 연구

LLM 심판이 쓸 만한 측정 도구라는 근거는 논문에 꽤 있습니다. 확인해야 할 것은 그 결과를 어느 도메인에서 측정했느냐입니다.

MT-Bench 연구에서 GPT-4 심판은 해당 대화 데이터의 통제·크라우드 사람 선호와 80% 넘게 일치했고, 이는 같은 연구에서 사람끼리 일치한 비율과 비슷했습니다.[^mtjudge] <span class="term" data-tip="평가 기준과 단계별 평가 절차를 LLM에 주고 생성된 점수 확률을 이용해 응답 품질을 채점하는 프레임워크. 이 프로젝트는 그 기준 축을 진단에만 사용하고 전체 순위는 pairwise 결과로 낸다.">G-Eval</span>은 요약 과제에서 사람 점수와 <span class="term" data-tip="두 변수의 순위를 비교하는 비모수 상관계수. 1은 같은 순서, -1은 완전히 반대 순서이며 0은 순위 사이의 단조 관계가 관측되지 않았다는 뜻이다.">Spearman</span> 0.514를 보고했습니다. 의미 기반 <span class="term" data-tip="평가할 기준과 각 기준의 판단 수준을 미리 적은 채점 지침. 이름만 나열하지 않고 기준 설명과 점수 앵커를 함께 줘야 평가자마다 뜻이 달라지는 문제를 줄일 수 있다.">루브릭</span> 평가가 기존 자동 지표보다 사람 판단에 가까울 수 있다는 결과입니다.[^geval-judge] 다만 둘 다 대화와 요약에서 측정한 값이고, 아동 동화 데이터는 아닙니다.

반대 방향의 결과도 있습니다. EMNLP 2024 메타평가는 자동 평가의 타당도가 과제와 참조 답안 유무에 크게 좌우된다고 보고했습니다. 참조 답안을 빼자 GPT-4 심판의 효과도 크게 떨어졌습니다.[^judge-context]

또 다른 EMNLP 연구에서는 짧은 공격 문구 하나로 절대 점수를 부풀릴 수 있었고, 절대 채점이 상대 비교보다 공격에 취약했습니다.[^judge-attack] 그래서 강한 모델 하나에게 1~10점을 물으면 객관적일 것이라는 가정은 쓰지 않았습니다.

Little Bard가 절대 점수 하나 대신 상대 비교와 여러 계열의 심판단을 쓴 것도 이 때문입니다. PoLL 연구는 3가지 심판 설정과 6개 데이터셋에서, 서로 다른 계열의 작은 모델 패널이 대형 심판 하나보다 성능이 좋고 계열 내 편향도 적었다고 보고했습니다. 비용은 7배 넘게 낮았습니다.[^poll-judge]

물론 이 결과가 Little Bard의 정확도를 증명하지는 않습니다. 심판 한 명의 취향을 여러 계열의 독립 판정으로 희석한다는 설계에 근거가 하나 더해진 정도입니다.

### 8-3. 심판 판정을 믿기 위한 조건

Little Bard에서 심판 판정을 신뢰하려면 아래 조건을 모두 충족해야 합니다.

1. 생성 모델명을 숨기고 같은 본문 상한을 적용합니다.
2. <span class="term" data-tip="두 대안을 같은 평가 질문 아래 비교하는 방식. 이 평가 앱에서는 익명화한 Story A와 Story B 중 더 나은 동화를 고르게 한다.">A/B</span>와 B/A를 모두 판정해 위치 효과를 쌍·심판 단위 안에서 평균냅니다.
3. 서로 다른 계열의 심판을 쓰고 생성 모델과 같은 계열 심판은 제외합니다.
4. 파싱하지 못한 응답은 무승부로 꾸미지 않고 `invalid`로 제외합니다.
5. 심판별 판정과 불일치, 프롬프트·루브릭·<span class="term" data-tip="같은 모델 저장소 안의 특정 커밋이나 버전 식별자. 학습·변환·서빙에서 같은 리비전을 고정해야 조용한 파일 변경으로 결과가 달라지는 일을 막을 수 있다.">모델 리비전</span>을 보존합니다.
6. 대표 표본을 사람이 같은 방식으로 평가해 사람-심판 일치와 사람끼리의 일치를 함께 보고합니다.
7. 근소한 순위, 심판 불일치가 큰 쌍, 안전 관련 판정은 자동 결론 대신 사람 검토로 올립니다.

이 중 가장 중요한 것은 여섯 번째입니다. 외부 논문에서 GPT-4가 80% 넘게 일치했다고 해서 우리 동화 심판도 그렇다는 보장은 없습니다. 같은 `childlit-v3` 프롬프트와 실제 후보 동화로 사람 골든셋을 만들어 일치도를 측정해야 이 도메인에서 믿을 만한지 판단할 수 있습니다. 일치도가 낮으면 루브릭과 심판 구성을 다시 고치거나, 확실한 사례만 자동 판정하고 나머지는 사람에게 넘기는 선별 평가로 가야 합니다. 신뢰도에 따라 자동 판정과 사람 검토를 나눈 연구는, LLM 판정을 모두 받아들이는 방식보다 사람 일치를 더 강하게 보장할 수 있다고 보였습니다.[^trust-escalate]

### 8-4. 현재 진행 상황

현재 상태도 적어 둡니다. `childlit-v3` 생성 정책과 `childlit-strict-v3` 심판 정책은 코드에 반영했습니다. 새 정책으로 유료 심판 스모크를 돌리는 일과, 아동문학·영어교육 관점을 넣은 사람 골든셋 교정은 아직 끝내지 못했습니다.

과거 $46.76 런은 레거시 정책 결과입니다. 파싱 실패를 무승부로 처리했고, 축 출력이 오염됐고, 자기 계열 판정도 섞여 있습니다. 그래서 새 심판이 타당하다는 근거로 다시 쓸 수 없습니다. 새 순위에 대해 지금 말할 수 있는 것은 “편향을 줄이고 검증할 수 있게 설계했다”까지입니다. 사람만큼 정확하다는 것은 아직 입증하지 못했습니다.

LLM 심판에게 기대하는 역할은 정답 없는 창작 비교를 대량으로 반복해 주는 신호입니다. 그 신호를 믿을지는 위 일곱 가지 조건을 통과하는지 보고 결정합니다.

## 마치며

공개 벤치마크는 순위 근거로 쓰지 않기로 했습니다. 포화와 오염, 도메인 불일치도 문제였지만, 무엇보다 아동 동화에서 봐야 할 난이도, 연령 적합, 안전을 재는 벤치마크가 없었습니다. 기성 API 모델은 계속 쓰되 그대로 믿지는 않습니다. <span class="term" data-tip="반복 생성이나 편집을 거치며 대상의 속성이 조금씩 원래 값에서 멀어지는 현상. 직전 결과를 입력으로 다시 쓰는 구조에서는 오차가 누적될 수 있다.">드리프트</span>와 단종은 공식 문서로도 확인되므로, 교체를 판정할 장치는 직접 갖고 있어야 합니다.

자체 모델이 비용과 보안의 답이라고 미리 정하지도 않았습니다. 데이터 경계, 품질, 유효 응답률, 지연, 실제 운영 원가를 모두 통과해야 기본 경로로 바꿉니다. 평가 기준은 학습보다 먼저 만듭니다. 파인튜닝이 성공했는지는 같은 기준으로 잰 전후 점수 차와 그 신뢰구간으로만 말할 수 있습니다. 다음 편에서는 Bradley-Terry 쌍대 비교를 고른 이유를 정리합니다.
