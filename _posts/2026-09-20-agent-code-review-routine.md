혼자 하는 작업이어도 리뷰 없이 머지하지 않기로 했습니다. 사람이 매번 리뷰할 수는 없어서, 별도 세션의 에이전트가 <span class="term" data-tip="변경한 코드를 원래 브랜치에 합치기 전에 제출하는 요청. 무엇이 어떻게 바뀌는지 변경 내역으로 보여주고 검토를 거친다.">풀 리퀘스트</span>를 리뷰하고 머지하도록 구성했습니다. 사흘 동안 PR 네 건에 리뷰를 여섯 번 돌렸고, 차단 다섯 건이 나왔습니다. 다섯 건 모두 제가 만든 실제 결함이었습니다.

처음 몇 번은 리뷰가 코드를 읽고 그럴듯한 소견만 냈습니다. 리뷰가 직접 측정하고 실험까지 하게 된 건 프롬프트를 바꾼 뒤였습니다. 아래에서는 리뷰가 잡은 결함과 프롬프트에 무엇을 적었는지를 정리했습니다.

## 1. 세션을 분리한 이유

같은 세션에서 리뷰를 시키면 코드를 작성할 때의 맥락이 그대로 따라갑니다. "왜 이렇게 했는지"를 이미 납득한 상태라서, 앞서 내린 판단을 뒤집는 쪽으로 잘 가지 않습니다.

별도 세션에는 diff와 검증 기준만 전달했습니다. 제가 왜 그렇게 작성했는지는 모르는 상태입니다. 이번에 잡힌 다섯 건 중 세 건은 제가 "이 정도면 됐다"고 판단하고 넘어간 자리에서 나왔습니다.

## 2. 리뷰가 찾은 결함

리뷰가 차단한 다섯 건은 다음과 같습니다.

| 지적 | 성격 |
|---|---|
| 심사에 보내는 발췌에서 원고가 쪽마다 정한 인물별 반응·시선이 빠졌다 | 안전 판정 사각지대 |
| 같은 발췌에서 표지 계획의 시선이 빠졌다 | 같은 계열 |
| 새 교정문 필드로 <span class="term" data-tip="심사가 지적한 자산만 골라 다시 생성하는 단계. 한 번만 수행하고 그 결과를 다시 심사하지 않으면, 교정이 빗나가도 그대로 출고된다.">재작화</span> 접미사가 몫을 290자 초과한다 | 재작화 유실 |
| 밀도 계측 교정이 겹치면 공급자 상한을 초과한다 | 라운드 전체 연쇄 실패 |
| 완화한 말풍선 계약이 쪽마다 실리는 고정 블록에는 미반영 | 계약 불일치 |

앞의 두 건이 대표적입니다. 발췌를 만들 때 "고정 규칙은 우리가 쓴 글이라 위험이 들어올 경로가 아니다"라는 기준을 세웠습니다. 기준 자체는 맞았지만 분류가 틀렸습니다.

원고가 인물마다 정하는 반응과 시선은 사용자에게서 온 값입니다. 그런데 얼굴 규칙 블록 안에 들어 있다는 이유로 고정 규칙에 분류해 버렸습니다. 이 값은 장면 블록에도 조연 시트에도 없어서, 발췌에서 빠지면 어떤 심사도 볼 수 없습니다.

리뷰는 이 문제를 말로 설명하지 않고 실제 값을 출력해서 보여 줬습니다.

```text
PageCharacterCueSnapshot(
    name="the neighbour",
    reaction="... holding a lit match over the child's hands",
    gaze_target="... the bottle of pills on the floor",
)
→ 생성 프롬프트 포함: True
→ 심사 발췌 포함: False
```

같은 값이 생성 프롬프트에는 들어가고 심사 발췌에서는 빠진다는 것을 한눈에 확인할 수 있었습니다.

## 3. 리뷰 프롬프트 작성 방법

처음 몇 번은 "이 관점으로 확인해라"만 적었습니다. 리뷰는 diff를 읽고 그럴듯한 소견을 냈지만, 수치가 없어서 받아들일지 판단하기 어려웠습니다. 프롬프트를 아래처럼 바꾼 뒤로 리뷰가 달라졌습니다.

### 3-1. 확인할 불변을 숫자로 적기

"안전한지 봐라" 대신 "이 값이 이 상한 아래인지 직접 재어라"로 적었습니다. 실제로 넣은 문구는 다음과 같습니다.

```text
- 교정문 상한·줄바꿈 접기가 기존 필드와 같게 적용되는지.
  최악 가정(레터링 교정 811자 + 새 문단 600자 + 참조 불일치 600자)이
  교정문 몫(2,000자) 안에 드는지, 묶음 상한(31,900)을 위협하지 않는지.
```

이렇게 적자 리뷰가 워크트리를 따로 만들고 조합별로 길이를 재서 표로 돌려줬습니다. 앞의 다섯 건 중 세 건이 이 방식에서 나왔습니다.

### 3-2. 테스트가 실제로 잡는지 실험하게 하기

테스트를 추가했다는 말만으로는 부족해서, 테스트가 정말 깨지는지 확인하는 지시를 넣었습니다.

```text
- 갱신된 회귀 테스트가 진짜로 불변을 고정하는지
  (상한을 일부러 다시 600자로 돌리면 깨지는지) 실험해 확인하라.
```

리뷰는 실제로 상수를 되돌리고 테스트를 돌렸습니다. 테스트가 깨지는 것을 확인한 뒤 "통과하는 최대 상한은 245자라 220은 25자 여유"라고 보고했습니다. 제가 PR에 "테스트를 추가했다"고 쓴 것보다 이 한 줄이 더 쓸모 있었습니다.

### 3-3. 알려진 환경 실패를 미리 알려 주기

리뷰가 도는 환경에서는 컨테이너 기반 통합 테스트가 돌지 않습니다. 이 사실을 적어 두지 않으면 리뷰가 "테스트 18개 실패"를 결함으로 올립니다. 그래서 프롬프트에 "그 실패는 도커 미가용 때문이니 <span class="term" data-tip="Confidence Interval의 약칭. 이 글에서는 추정 불확실성을 나타내는 신뢰구간을 뜻하며 CI/CD의 CI와는 다른 용어다.">CI</span> 결과로 대신하라"고 적었습니다. 계속 실패 중인 워크플로가 있으면 그 사실과 근거(언제부터, 어느 브랜치에서)도 함께 적었습니다.

### 3-4. 하지 말 것을 명시하기

코드 수정 후 push, 브랜치 생성, 이슈 상태 변경, 배포 워크플로 실행, 관리형 프롬프트 변경은 금지 목록에 넣었습니다. 리뷰어는 문제를 발견하면 직접 고치려고 합니다. 그대로 두면 리뷰와 작성이 다시 한 세션으로 합쳐집니다.

## 4. 리뷰의 제안을 그대로 따르지 않은 사례

네 번째 지적에서 리뷰는 예산 재분배를 제안했습니다. 교정문 몫을 2,600자로 올리고 쪽 예산을 29,400자로 내리는 안이었습니다. 산술은 맞았습니다.

그 값으로 바꾸고 회귀 테스트를 돌려 보니, 조연이 여덟 명인 책에서 상세 설명이 전부 사라졌습니다. 그래서 다른 해법을 선택했고, 제안을 따르지 않은 이유를 측정값과 함께 답글로 남겼습니다. 다음 리뷰에서 그 판단이 받아들여졌습니다.

이후로는 지적이 오면 먼저 재현되는지 확인하고, 해법은 근거를 따로 보고 고르고 있습니다.

## 5. 남은 문제

리뷰 본문 끝에 도구 서명이 붙는 문제가 있습니다. 팀 규칙상 쓰면 안 되는 문구라 프롬프트에 금지를 명시했지만 종종 붙습니다. 사흘 동안 세 번 붙었고, 그때마다 지웠습니다.

시간과 비용도 듭니다. 리뷰 한 번에 5~12분이 걸리고, diff를 읽고 워크트리를 만들어 테스트를 돌리는 만큼 <span class="term" data-tip="모델의 토크나이저가 텍스트를 나눈 처리 단위. 한 토큰은 단어 하나와 같지 않으며 같은 문장도 모델별 토크나이저에 따라 토큰 수가 달라질 수 있다.">토큰</span>을 씁니다. 파일 한두 개를 고치는 변경에 같은 강도의 리뷰를 붙이는 건 낭비입니다.

## 마치며

별도 세션의 에이전트 리뷰를 도입해 사흘 동안 차단 다섯 건을 받았고, 모두 실제 결함이었습니다. 리뷰가 코드를 읽는 데서 멈추지 않게 만든 건 확인할 불변을 숫자로 적고, 테스트를 직접 깨 보게 한 프롬프트 문구였습니다.

지금은 불변이 걸린 변경, 안전 판정에 닿는 변경, 프롬프트 계약을 바꾸는 변경에만 이 리뷰를 돌리고 있습니다. 도구 서명이 붙는 문제는 아직 해결하지 못했습니다.
