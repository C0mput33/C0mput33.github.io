혼자 하는 작업이어도 리뷰 없이는 머지하지 않기로 했다. 그렇다고 사람이 매번 붙을 수는 없어서, 별도 세션의 에이전트가 <span class="term" data-tip="변경한 코드를 원래 브랜치에 합치기 전에 제출하는 요청. 무엇이 어떻게 바뀌는지 변경 내역으로 보여주고 검토를 거친다.">풀 리퀘스트</span>를 리뷰하고 머지하게 했다. 사흘 동안 PR 네 건에 리뷰를 여섯 번 돌렸다. 차단이 다섯 건 나왔는데, 하나도 빠짐없이 내가 만든 실제 결함이었다.

처음 몇 번은 리뷰가 코드를 읽고 그럴듯한 말만 했다. 직접 재 보고 실험까지 하게 된 건 프롬프트 문구를 바꾼 다음이다.

## 굳이 세션을 나눈 이유

같은 세션에서 리뷰를 시키면 내가 코드를 쓸 때의 맥락이 그대로 따라간다. "왜 이렇게 했는지"를 이미 알고 납득한 상태라, 앞서 내린 판단을 잘 뒤집지 않는다.

별도 세션에는 diff와 검증 기준만 줬다. 내가 왜 그렇게 썼는지는 모르는 상태다. 이번에 잡힌 다섯 건 중 셋이 내가 "이 정도면 됐다" 하고 넘어간 자리에서 나왔다.

## 잡힌 결함

| 지적 | 성격 |
|---|---|
| 심사에 보내는 발췌에서 원고가 쪽마다 정한 인물별 반응·시선이 빠졌다 | 안전 판정 사각지대 |
| 같은 발췌에서 표지 계획의 시선이 빠졌다 | 같은 계열 |
| 새 교정문 필드로 <span class="term" data-tip="심사가 지적한 자산만 골라 다시 생성하는 단계. 한 번만 수행하고 그 결과를 다시 심사하지 않으면, 교정이 빗나가도 그대로 출고된다.">재작화</span> 접미사가 몫을 290자 초과한다 | 재작화 유실 |
| 밀도 계측 교정이 겹치면 공급자 상한을 초과한다 | 라운드 전체 연쇄 실패 |
| 완화한 말풍선 계약이 쪽마다 실리는 고정 블록에는 미반영 | 계약 불일치 |

처음 두 건이 아팠다. 발췌를 만들 때 "고정 규칙은 우리가 쓴 글이니 위험이 들어올 경로가 아니다"라는 기준을 세웠었다. 기준은 맞았다. 분류를 틀렸다.

원고가 인물마다 정하는 반응과 시선은 사용자에게서 온 값이다. 나는 그게 얼굴 규칙 블록 안에 들어 있다는 이유만으로 고정 규칙에 묶어 버렸다. 이 값은 장면 블록에도 조연 시트에도 없어서, 발췌에서 빠지면 어떤 심사도 못 본다.

리뷰는 이걸 말로 풀지 않고 실제 값을 찍어 보여 줬다.

```text
PageCharacterCueSnapshot(
    name="the neighbour",
    reaction="... holding a lit match over the child's hands",
    gaze_target="... the bottle of pills on the floor",
)
→ 생성 프롬프트 포함: True
→ 심사 발췌 포함: False
```

## 프롬프트에 적은 것

처음 몇 번은 "이 관점으로 확인해라"만 적었다. 리뷰는 diff를 읽고 그럴듯한 소견을 냈다. 그런데 수치가 하나도 없어서 받아들일지 말지 정할 수가 없었다. 프롬프트를 아래처럼 바꾸고 나서야 리뷰가 달라졌다.

### 확인할 불변을 숫자로 적는다

"안전한지 봐라"라고 쓰지 않고 "이 값이 이 상한 아래인지 직접 재어라"라고 쓴다.

```text
- 교정문 상한·줄바꿈 접기가 기존 필드와 같게 적용되는지.
  최악 가정(레터링 교정 811자 + 새 문단 600자 + 참조 불일치 600자)이
  교정문 몫(2,000자) 안에 드는지, 묶음 상한(31,900)을 위협하지 않는지.
```

이렇게 적었더니 리뷰가 워크트리를 따로 만들고 조합마다 길이를 재서 표로 돌려줬다. 앞의 다섯 건 중 셋이 이 방식으로 나왔다.

### 테스트가 정말 잡는지 실험하게 한다

```text
- 갱신된 회귀 테스트가 진짜로 불변을 고정하는지
  (상한을 일부러 다시 600자로 돌리면 깨지는지) 실험해 확인하라.
```

리뷰는 실제로 상수를 되돌리고 테스트를 돌렸다. 테스트가 깨지는 걸 확인한 다음 "통과하는 최대 상한은 245자라 220은 25자 여유"라고 보고했다. 내가 PR에 "테스트를 추가했다"고 쓴 것보다 이 한 줄이 훨씬 쓸모 있었다.

### 이미 알고 있는 환경 실패는 미리 말해 둔다

리뷰가 도는 환경에서는 컨테이너 기반 통합 테스트가 안 돈다. 이걸 안 적어 두면 리뷰가 "테스트 18개 실패"를 결함으로 올린다. 그래서 프롬프트에 "그 실패는 도커 미가용 때문이니 <span class="term" data-tip="Confidence Interval의 약칭. 이 글에서는 추정 불확실성을 나타내는 신뢰구간을 뜻하며 CI/CD의 CI와는 다른 용어다.">CI</span> 결과로 대신하라"고 적는다. 계속 실패 중인 워크플로가 있으면 그 사실과 근거(언제부터, 어느 브랜치에서)도 같이 적어 준다.

### 하지 말 것을 적는다

코드 수정 후 push, 브랜치 생성, 이슈 상태 변경, 배포 워크플로 실행, 관리형 프롬프트 변경은 금지 목록에 넣었다. 리뷰어는 문제를 찾으면 직접 고치고 싶어 한다. 내버려 두면 리뷰와 작성이 다시 한 세션으로 합쳐진다.

## 리뷰가 낸 해법을 따르지 않은 일

네 번째 지적에서 리뷰는 예산을 다시 나누자고 했다. 교정문 몫을 2,600자로 올리고 쪽 예산을 29,400자로 내리자는 안이었다. 산술은 맞았다.

그 값으로 바꾸고 회귀 테스트를 돌려 봤다. 조연이 여덟 명인 책에서 상세 설명이 통째로 사라졌다. 나는 다른 해법을 골랐고, 제안을 따르지 않은 이유를 측정값과 함께 답글로 달았다. 다음 리뷰는 그 판단을 받아들였다.

그 뒤로는 지적이 오면 재현되는지부터 보고, 해법은 따로 근거를 보고 고른다.

## 남은 문제

리뷰 본문 끝에 도구 서명이 붙는다. 팀 규칙상 쓰면 안 되는 문구라 프롬프트에 금지를 적었는데도 종종 붙는다. 사흘 동안 세 번 붙었고, 그때마다 지웠다.

시간과 비용도 든다. 리뷰 한 번에 5~12분이다. diff를 읽고 워크트리를 만들어 테스트까지 돌리니 <span class="term" data-tip="모델의 토크나이저가 텍스트를 나눈 처리 단위. 한 토큰은 단어 하나와 같지 않으며 같은 문장도 모델별 토크나이저에 따라 토큰 수가 달라질 수 있다.">토큰</span>도 그만큼 나간다. 파일 한두 개 고친 변경에까지 이렇게 돌리는 건 아깝다. 지금은 불변이 걸렸거나, 안전 판정에 닿거나, 프롬프트 계약을 바꾸는 변경에만 돌린다.
