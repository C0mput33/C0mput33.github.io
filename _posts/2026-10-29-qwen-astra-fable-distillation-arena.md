Astra 160편과 Fable 140편의 영어동화 원고로 <span class="term" data-tip="총 파라미터 약 35B 중 토큰마다 약 3B를 선택하는 MoE 구조. 전체 가중치 메모리는 필요하며 실제 속도는 라우팅·메모리 대역폭·커널·캐시에 따라 달라진다.">Qwen3.6-35B-A3B</span>를 다시 학습했습니다. 자동 비교만으로 새 학습본이 학습 전보다 일관되게 좋아졌다고 결론 내리지 못했습니다. 24개 문제의 직접 비교는 새 학습본 10승, 학습 전 15승, 평균 동점 19건입니다. 별도로 고정한 12개 문제에서는 새 학습본 10승, 학습 전 5승, 평균 동점 9건이 나왔습니다. 한 문제에 심판 두 개가 각각 판정하며, 순서 교환 결과가 뒤집힌 경우도 평균 동점에 포함됩니다.

이 글은 2026년 10월 29일 로컬 실험의 기록입니다. 생성·검토·학습·평가는 코딩 에이전트로 실행했습니다. 사람 편집자나 실제 아동의 평가 결과가 아니며 운영 앱에는 연결하지 않았습니다.

[설정과 실측 JSON](/assets/data/experiments/qwen-frontier-teachers-20261029/measurements.json), [별도 12문제 확인](/assets/data/experiments/qwen-frontier-teachers-20261029/confirmation.json)에 수치를 남겼습니다.

## 1. 교사 모델을 바꾸되 과거 기록은 남겼습니다

[앞선 실험]({% post_url 2026-10-29-qwen-story-sft-302-manuscripts %})에서는 DeepSeek 152편과 Kimi 150편으로 Qwen을 학습했습니다. 그 글의 교사 이름을 Astra와 Fable로 바꾸면 실제로 수행한 실험과 달라집니다. 따라서 기존 결과는 남기고 새 교사 원고로 별도의 학습을 진행했습니다.

이번에 선택한 교사는 <span class="term" data-tip="여러 회사의 LLM을 하나의 API와 결제로 호출하게 해주는 중계 서비스. 모델마다 계정을 따로 만들 필요가 없어 다모델 비교 실험에 편하다.">OpenRouter</span>의 `openai/gpt-6-astra`와 `anthropic/claude-fable-5.1`입니다. 두 모델이 모든 글쓰기에서 가장 좋다고 확정한 것은 아닙니다. 북끼끼의 영어동화 요청에서 이 모델들의 원고를 직접 비교하고, 그 원고를 배운 Qwen의 변화까지 확인하는 것이 목표였습니다.

여기서 <span class="term" data-tip="큰 모델의 동작을 더 작거나 빠른 모델에 옮겨 담는 학습 기법. 원 모델의 출력이나 중간 표현을 학생 모델의 학습 신호로 쓴다.">증류</span>라고 부르는 작업은 교사의 완성 응답을 목표로 삼는 <span class="term" data-tip="Supervised Fine-Tuning. 입력과 목표 응답 쌍을 주고 다음 토큰 손실을 줄이도록 모델을 추가 학습하는 단계. 선호쌍을 비교하는 DPO와 데이터 형식과 목적이 다르다.">SFT</span>입니다. 교사 모델의 가중치나 내부 확률을 가져오지 않았습니다. 새 원고는 기존 학습 <span class="term" data-tip="동결한 베이스 모델 옆에 붙여 학습하는 작은 추가 가중치 묶음. 파일이 작아도 층 이름과 배열 모양이 실행 프레임워크의 형식과 맞지 않으면 그대로 옮겨 쓸 수 없다.">어댑터</span> 위에 이어 학습하지 않고, 같은 Qwen 기반 가중치에서 시작한 별도 어댑터에 사용했습니다.

### 1-1. API 접근과 학습 이용 허가는 다릅니다

처음에는 `enforce_distillable_text: true`로 두 교사 모델을 요청했지만, 기본 증류 허용 경로를 찾지 못했습니다. 생성 <span class="term" data-tip="소프트웨어가 다른 소프트웨어의 기능이나 데이터에 접근할 때 따르는 호출 계약. 사용할 주소, 입력 형식, 인증, 응답과 오류 규칙을 함께 정의한다.">API</span>를 호출할 수 있다는 사실만으로 학습 이용까지 허용됐다고 처리하지 않았습니다. 별도 허가를 확인했다는 프로젝트 소유자의 응답을 받은 뒤, 그 확인을 이번 작업의 이용 근거로 기록했습니다. 계약 원문을 제가 독립적으로 검증한 것은 아닙니다. 이 경로를 모든 사용자가 일반적으로 이용할 수 있다는 의미도 아닙니다.[^routing]

## 2. 기존 원고가 아닌 소재와 조건을 재사용했습니다

기존 데이터에서 이야기 소재, 지킬 사실, 결말, 주의할 행동만 가져왔습니다. DeepSeek나 Kimi가 쓴 기존 완성 원고는 새 교사 요청과 새 학습 목표에 포함하지 않았습니다. 여기에 세탁소, 가족 엽서, 실내 놀이, 박물관 관찰 등 가상의 새 소재를 보탰습니다. 실제 아이의 인터뷰나 개인정보는 보내지 않았습니다.

요청은 평가앱의 현재 생성 규약에 맞췄습니다. 7세 아이와 어른이 함께 읽는 180~230단어의 본문이며 제목과 고정 문단 수는 요구하지 않았습니다. 이전 실험은 제목과 여섯 문단을 요청했으므로 교사만 교체한 통제 실험은 아닙니다. 학습률도 함께 조정했으며, 개선이 있더라도 어느 변경 하나의 효과로 분리할 수 없습니다.

짧은 문장만 많이 쌓으면 모든 이야기가 같은 모양으로 끝나기 쉽습니다. 그래서 작은 문제 해결, 관찰, 조용한 감정 변화, 누적되는 반복, 협동, 순환형 결말을 함께 사용했습니다. 반복 자체를 결함으로 보지 않고 앞선 사건에 어떤 변화를 더하는지 확인했습니다.


최종 학습에는 300편, 검증에는 24편을 사용했습니다. 학습 원고의 구성은 창작 144편, 가상 아이 경험 105편, 가상 일기 47편, 상호작용 장면 2편, 고전 각색 1편, 공개 원문 리라이트 1편입니다. 유명 동화책을 대량으로 학습했다고 설명할 수 있는 구성은 아닙니다. 원문을 사용하는 사례에는 저자·URL·라이선스·각색 여부를 별도로 기록했습니다.

학습 전 후보 39편을 원문 대조했고, 이 중 최종 학습·검증에 들어간 것은 28편입니다. 모든 원고를 사람이 읽고 승인했다는 의미가 아닙니다. 같은 작품 그룹이 학습과 검증에 겹치지 않는지, 목표 텍스트가 중복되지 않는지, 전체 요청과 응답이 잘리지 않는지도 검사했습니다.

## 3. 자동 검토가 정상 표현을 오류로 잡았습니다

원고마다 분량과 출력 형식을 검사하고 Kimi에 사건, 수량, 소유자, 행동, 영어 표현을 검토하도록 요청했습니다. 지적된 문장을 원고에서 찾을 수 있는지 확인하고, 근거가 있는 지적만 수정 요청에 전달했습니다. 통과하지 못한 일부는 다른 교사 모델로 다시 읽었습니다.

그런데 인용이 실제로 존재해도 판단은 틀릴 수 있었습니다. 의인화된 수달 이야기의 “He knelt by the other two stones”를 두고 검토 모델이 수달에게 무릎이 없어 불가능하다고 지적했습니다. 이미 동물들이 사람처럼 행동하는 동화에서 이 문장만 모순으로 처리할 근거는 부족했습니다. 이런 판정을 모두 고치면 원고가 오히려 어색해질 수 있습니다.

반대로 자동 통과 원고에서도 소재의 문제가 보였습니다.

| 사례 | 확인한 점 | 처리 |
|---|---|---|
| 땅에 묻은 무화과와 싹 | 정확히 7일 만에 싹이 난다는 입력의 근거가 확인되지 않음 | 제외 |
| 매주 나타나는 노란 장갑 | 여우에게 장갑이 있다는 결말만으로 반복과 실의 단서가 설명되지 않음 | 제외 |
| 밤마다 짧아지는 연필 | 잘린 실에 대한 아빠의 설명과 잠결에 그리는 동생이 별개로 이어짐 | 제외 |
| 담요 안의 그림자 곰 | 턱 아래 손전등과 벽에 비친 머리 그림자의 배치가 불명료함 | 제외 |
| 문이 삐걱거리는 후렴 | 같은 소리가 네 번 등장하지만 소리의 정체를 알아가는 장면이 진행됨 | 횟수만으로 탈락시키지 않음 |

별도 원문 대조는 코딩 에이전트가 수행했습니다. 사람이 편집하거나 부모와 아이가 평가한 데이터는 아닙니다. 검토 모델의 통과가 사실성이나 연령 적합성을 보증하지 않는다는 한계는 그대로 남습니다.

## 4. 검증 원고로 저장 가중치를 선택했습니다

첫 실행은 <span class="term" data-tip="대량의 수치 연산을 병렬 처리하는 프로세서. LLM에서는 행렬 연산을 빠르게 수행하지만 모델 적재 가능 크기는 연산 성능뿐 아니라 GPU 메모리에도 제한된다.">GPU</span> 메모리 부족으로 첫 업데이트 전에 중단됐습니다. 캐시 한도를 낮춘 두 번째 실행도 같은 지점에서 멈췄습니다. 이번 입력의 최대 길이는 1,203토큰으로 이전 실험의 789토큰보다 길었습니다. 공통 시스템 지시문만 짧게 바꿔 최대 828토큰으로 줄였고, 개별 요청과 완성 원고가 바이트 단위로 그대로인지 확인했습니다. 비교 평가의 요청은 바꾸지 않았습니다. 실패 로그와 변경 전 데이터도 남겼습니다.

축약 후 실행은 진행됐지만 처리 속도가 낮아 초기에 중단했습니다. 캐시 한도를 256MiB에서 2GiB로 조정하고 같은 기반 가중치·데이터·시드로 다시 시작했습니다. 다른 앱이나 사용자의 프로세스는 종료하지 않았습니다. 입력 길이와 캐시 설정을 함께 바꿨으므로 어느 하나가 메모리 실패의 단독 원인이었다고 결론 내리지는 않았습니다.

학습은 기존과 같은 Mac의 <span class="term" data-tip="Apple이 애플 실리콘용으로 만든 배열·머신러닝 프레임워크. CPU와 GPU가 공유하는 통합 메모리 모델을 사용하며 추론과 학습을 지원한다.">MLX</span> <span class="term" data-tip="원본 가중치는 얼려 두고 곁에 붙인 작은 저랭크 행렬(어댑터)만 학습하는 파인튜닝 기법. 학습 대상이 전체의 1% 미만이라 메모리와 시간이 크게 줄고, 어댑터만 따로 저장·교체할 수 있다.">LoRA</span>로 실행했습니다. 4bit Qwen3.6-35B-A3B의 마지막 여덟 층에 있는 일반 attention과 <span class="term" data-tip="어텐션 계산을 시퀀스 길이에 비례(선형)하도록 근사하는 방식. 긴 문맥에서 메모리와 속도가 유리해 최신 하이브리드 모델이 다수 층에 채택하지만, 표준 어텐션과 구현이 달라 학습·서빙 도구의 지원 여부를 따로 확인해야 한다.">linear attention</span>을 모두 포함했습니다. 설정 파일만 확인하지 않고 실제 학습 가능한 텐서의 층 번호도 확인했습니다.[^mlx]

이전 어댑터가 새 요청에서 끝없이 반복한 사례를 보고 학습률을 `3e-5`에서 `1e-5`로 낮췄습니다. 더 작은 업데이트가 반복을 줄일 것이라는 가설이며, 결과가 나오기 전부터 해결됐다고 보지는 않았습니다. 한 차례의 학습을 수행하고 중간 가중치를 저장했습니다.

선택 기준은 검증 원고의 NLL입니다. 학습 로그의 평가 시점과 저장 시점이 다르므로, 로그에 적힌 가장 낮은 숫자를 그대로 선택하지 않고 실제 저장 파일을 다시 불러 점수를 측정했습니다. 비교 문제의 <span class="term" data-tip="이 시스템의 최종 점수. BT로 추정한 실력값을 체스 레이팅처럼 읽히도록 평균 1000 기준으로 변환한 것. 두 모델의 점수 차가 곧 승률로 환산된다(차이 100이면 약 64%, 400이면 약 91%).">Arena 점수</span>로 저장 가중치를 고르지 않았습니다.

실제 학습 가능한 파라미터는 6,500,352개였으며 층 번호 32~39의 여덟 층이 포함됐습니다. 검증 NLL은 기반 모델 1.8312, 선택한 가중치 1.4304였습니다. 선택 파일은 `0000300_adapters.safetensors`이며 가중치 SHA-256은 `5afb412982b4b861f85a9227aa83eef8f844645a8c28e3392914962c7e377152`입니다. NLL 감소만으로 동화의 재미나 사실성이 향상됐다고 판정하지는 않았습니다.

## 5. 기존 평가앱의 계산을 그대로 사용했습니다

새 문제 24개를 먼저 고정하고 Astra, Fable, 학습 전 Qwen, 기존 302편 SFT를 실행했습니다. 새 학습이 끝난 뒤 같은 문제에 새 Qwen을 추가했습니다. 기존 모델의 출력과 심판 결과를 유리하게 다시 생성하지 않았습니다.

평가에는 실제 Arena 앱의 `childlit-v3` 생성 요청과 `childlit-strict-v3` 심판 규약, 엄격한 판정 파서, <span class="term" data-tip="맞대결 승패만으로 각 후보의 숨은 실력을 추정하는 통계 모델(1952). 실력 차가 승률을 정한다고 가정하고, 관측된 모든 승패를 가장 잘 설명하는 실력값을 최우도로 찾는다. 경기 순서와 무관하게 같은 답이 나오는 배치 방식이라, 고정된 대전 기록의 순위에 적합하다.">Bradley-Terry</span> 계산을 사용했습니다.
