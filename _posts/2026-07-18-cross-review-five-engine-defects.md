[5편](/posts/46-dollar-frontier-live-eval-13-models/)의 실측 리포트를 정리하다가 모순 하나를 발견했습니다. 평가 시스템은 심판 <span class="term" data-tip="Large Language Model. 많은 텍스트에서 토큰의 조건부 분포를 학습해 문장을 생성하거나 분류·요약·추론 작업을 수행하는 언어 모델을 뜻한다.">LLM</span>이 자기 계열 모델을 평가하지 못하게 설계했고, 자기 계열에 후한 편향이 실측에서 t=6.43으로 잡히기도 했습니다. 그런데 정작 그 시스템의 코드는 만든 사람과 만든 에이전트만 검토해 왔습니다.

아래에서는 별도 에이전트에게 엔진 감사를 맡겨 찾은 결함 5개와, 각각을 어떻게 고치고 검증했는지 정리했습니다.

## 1. 감사 방식

7월 15일, 실측 데이터를 함께 넘기면서 별도의 AI 에이전트에게 엔진 전체 감사를 맡겼습니다. 요청 조건은 두 가지였습니다. 주석과 문서는 믿지 말고 코드만 볼 것, 칭찬하지 말고 결함을 찾을 것입니다.

돌아온 지적 가운데 검증을 통과한 것은 5개였습니다. 하나씩 코드로 다시 확인한 다음 수정하고 테스트를 추가했습니다.[^commit]

## 2. 발견한 결함과 수정

### 2-1. 심판 temperature가 0.7이었던 문제

<span class="term" data-tip="소프트웨어가 다른 소프트웨어의 기능이나 데이터에 접근할 때 따르는 호출 계약. 사용할 주소, 입력 형식, 인증, 응답과 오류 규칙을 함께 정의한다.">API</span> 호출 함수에 <span class="term" data-tip="다음 토큰 확률분포의 평탄함을 조절하는 값. 낮을수록 높은 확률의 토큰에 집중하지만 temperature 0도 제공자·모델·실행 환경에 따라 완전한 재현성을 보장하지 않는다.">temperature</span>가 하드코딩돼 있었습니다. 수정 전 코드는 다음과 같습니다.

```javascript
// 수정 전: 생성·번역·판정이 전부 이 함수 → 전부 temperature 0.7
body: JSON.stringify({model, messages, temperature: 0.7, ...})
```

동화 생성에는 다양성을 위해 0.7을 쓸 수 있습니다. 문제는 판정까지 같은 값으로 호출되고 있었다는 점입니다. 그만큼 호출마다 샘플링 변동이 커집니다. 파이썬 파이프라인의 심판은 처음부터 `temperature: 0.0`이었기 때문에, 두 구현 사이에도 차이가 있었습니다.

0으로 낮춘다고 완전히 해결되지는 않습니다. 변동은 줄지만 제공자와 모델 구현까지 고정되지는 않아서, 완전한 재현은 기대하지 않습니다.

수정 자체는 간단했는데요. 호출 함수에 옵션을 추가하고, 판정 두 번(정방향과 역방향)만 temp 0으로 보내도록 바꿨습니다.

```javascript
const r1 = await orCall(judge, SYS, user(A,B), {temp: 0});  // 판정 샘플링 변동 축소
const r2 = await orCall(judge, SYS, user(B,A), {temp: 0});  // 생성·번역은 별도 값 유지
```

### 2-2. 신뢰구간이 실제보다 좁게 계산된 문제

리더보드의 95% <span class="term" data-tip="Confidence Interval의 약칭. 이 글에서는 추정 불확실성을 나타내는 신뢰구간을 뜻하며 CI/CD의 CI와는 다른 용어다.">CI</span>를 만드는 <span class="term" data-tip="가진 데이터에서 복원추출로 여러 번 가짜 표본을 만들어 같은 계산을 반복하고, 그 결과들의 흩어짐으로 추정치의 불확실성을 재는 방법. 표본이 모집단을 대표한다면 재표집의 흔들림이 실제 추정 오차와 비슷하다는 원리다.">부트스트랩</span>에는 문제가 두 가지 겹쳐 있었습니다.

첫 번째는 반복 횟수가 60회였다는 점입니다. 데이터가 클수록 반복을 줄이도록(`n>1500 ? 60 : ...`) 작성돼 있어서, 정작 797쌍 실측에서는 60번만 재표집했습니다. 반복을 늘려서 줄일 수 있는 것은 <span class="term" data-tip="데이터를 작은 순서로 놓았을 때 일정 비율이 그 값 이하에 놓이도록 정한 경계값. 표본에서 백분위를 계산하는 보간 규칙은 도구마다 조금 다를 수 있다.">백분위</span> 끝값 자체의 <span class="term" data-tip="난수를 반복해서 뽑아 확률·기댓값·분포처럼 직접 계산하기 어려운 값을 근사하는 방법. 반복 횟수를 늘리면 시뮬레이션 오차는 보통 줄지만 잘못된 모델이나 표집 편향까지 고쳐주지는 않는다.">몬테카를로</span> 노이즈이고, 데이터 노이즈는 그대로입니다. 데이터가 크다는 이유로 반복을 줄인 것은 방향이 반대였습니다.

60개 표본에서 2.5백분위는 사실상 아래에서 한두 번째 값입니다. 극단 <span class="term" data-tip="표본을 작은 순서로 정렬했을 때 k번째 값처럼 위치로 정의되는 통계량. 최솟값, 중앙값, 최댓값과 표본 백분위가 여기에 포함된다.">순서통계량</span>은 표본이 적을수록 크게 흔들립니다. 결과적으로 끝점부터 흔들리는 <span class="term" data-tip="같은 절차로 표본을 반복 수집할 때 정해진 비율만큼 모수를 포함하도록 만든 구간. 두 개의 95% 신뢰구간이 겹치는지만으로 차이의 유의성을 판정할 수는 없다.">신뢰구간</span>이었습니다.

두 번째는 재표집 단위였습니다. 판정(contest)을 하나씩 독립으로 뽑았는데, 같은 쌍을 본 심판 3명의 판정은 서로 상관돼 있습니다. 상관된 값을 독립으로 다루면 분산이 작게 잡혀 CI가 실제보다 좁아집니다. 숫자만 틀리는 문제도 아니었습니다. <span class="term" data-tip="이 프로젝트의 은퇴 스케줄러. 배치(5권)마다 BT와 CI를 갱신하고, CI 분리가 2연속 확인된 모델만 은퇴시킨다. 한 번의 우연으로 탈락시키지 않는 확인 절차가 이름의 유래다.">retire2</span>가 바로 이 CI로 은퇴를 결정하기 때문에, CI가 좁으면 너무 일찍 은퇴하는 모델이 생길 수 있습니다.

당시에는 앱을 쌍(pair) 단위로 묶어 재표집하도록 바꾸고 반복을 1000회로 고정했습니다. 쌍 하나를 뽑으면 그 쌍의 심판 판정이 모두 함께 들어갑니다. 수정한 코드는 다음과 같습니다.

```javascript
for(let i=0;i<N;i++){
  const p = pairs[rand()*N | 0];               // 쌍 단위 복원추출
  for(const jd in p.juryScore)                  // 그 쌍의 심판 판정을 '함께'
    res.push({a:p.a.model, b:p.b.model, s:p.juryScore[jd]});
}
```

contest를 하나씩 뽑던 방식보다는 낫지만, 이것으로 모두 해결되지는 않습니다. 같은 프롬프트와 같은 동화가 여러 모델쌍에 반복해서 쓰이기 때문에 쌍끼리도 의존성이 남고, 프롬프트도 13개뿐입니다.

실측 리더보드가 어떻게 바뀌었는지는 7편에 따로 정리했습니다. 순위는 그대로였고 쌍-군집 CI가 평균 51% 넓어졌습니다. 이 구간도 프롬프트와 동화 재사용, 적응형 은퇴 경로까지는 반영하지 못하므로 최종 확증 CI로 읽으면 안 됩니다.

### 2-3. 파싱 실패가 무승부로 집계된 문제

심판 응답에서 승자를 뽑는 파서는 `Winner: A` 형식을 정규식으로 잡고, 잡지 못하면 tie(0.5)로 처리합니다. 심판이 `Winner is A`라고 쓰면 매치가 되지 않고, 그 판정은 아무 흔적 없이 무승부로 집계됩니다.

파이썬 쪽은 파싱 성공 여부(parse_ok)를 기록했지만 JS 쪽에는 이런 텔레메트리가 없었습니다. 2-1의 temperature 0.7 때문에 형식 이탈이 잦았다면, 결과가 0.5 쪽으로 끌려가고 있었을 수도 있습니다.

정규식을 넓히는 방법도 있었는데요, 일부러 택하지 않았습니다. 과거에 `\b` 없는 느슨한 정규식이 본문의 "the winner: **a** close call"에서 'a'를 A 승리로 잘못 파싱한 버그가 실제로 있었기 때문입니다. 정규식을 느슨하게 풀면 같은 종류의 조용한 오염이 다른 형태로 다시 생길 수 있습니다.

대신 실패가 드러나게 했습니다. 파싱 성공과 실패를 집계해서 실패하면 바로 로그에 경고를 남기고, 결과 화면 체크리스트에 파싱 성공률을 항상 표시합니다.

### 2-4. 빈 catch 블록

5편 중단 사고의 원인이었던 <span class="term" data-tip="브라우저가 출처별로 제공하는 동기식 문자열 키-값 저장소. Web Storage 한도는 브라우저에 따라 다르고 한도를 넘으면 QuotaExceededError가 날 수 있어 큰 체크포인트 저장에는 맞지 않는다.">localStorage</span> 침묵 실패를 이번에 근본적으로 수정했습니다. 용량을 측정해 보니 쌍당 약 13KB였습니다. 동화 3편이 약 4KB, 심판 3명 × 양방향 근거 전문이 약 9KB입니다. 10MB 한도라면 775쌍 근처에서 넘칩니다. 실제 797쌍 <span class="term" data-tip="진행 상태를 통째로 저장해둔 지점. 중단되거나 크레딧이 떨어져도 완료분을 다시 호출하지 않고 그 지점부터 이어서 실행할 수 있다.">체크포인트</span> 파일은 10.02MB였습니다. 5편의 중단은 미리 계산만 해 봤어도 예측할 수 있는 일이었습니다.

이제 저장에 실패하면 <span class="term" data-tip="브라우저가 출처별로 제공하는 비동기 객체 데이터베이스. localStorage보다 큰 구조화 데이터를 다루지만 저장 한도와 삭제 정책은 브라우저·디스크 여유·사용자 설정에 따라 달라진다.">IndexedDB</span>(사실상 무제한)로 즉시 전량 폴백합니다. 앱을 켤 때 IndexedDB 쪽 데이터가 더 완전하면 자동으로 복구해서 이어하기 지점을 잡습니다. 저장소는 localStorage(빠름), IndexedDB(무제한), GitHub(원격)의 3중 구조가 됐습니다.

### 2-5. 난이도 절대값의 낮은 신뢰도

5편 끝에 "<span class="term" data-tip="목표 난이도의 허용 범위(±밴드) 안에 들어온 비율. 절대 눈금이 틀린 측정기로 재면 실력과 무관하게 낮게 나올 수 있다.">Match Rate</span> 2.9%는 도구의 한계"라고 적었는데요. 어떤 한계였는지 여기서 설명해보겠습니다.

텍스트 난이도는 <span class="term" data-tip="글을 얼마나 수월하게 읽고 이해할 수 있는지를 뜻한다. 문장·단어 표면값으로 계산한 가독성 공식은 정량 단서일 뿐 의미 구조, 배경지식, 독자와 읽기 목적 전체를 대신하지 않는다.">가독성</span> 공식(Flesch-Kincaid, Coleman-Liau, <span class="term" data-tip="Automated Readability Index. 단어당 글자 수와 문장당 단어 수로 영어 텍스트의 미국 학년 수준을 추정하는 공식이다.">ARI</span> 합성)으로 측정하고, 그 학년을 <span class="term" data-tip="영어 독자의 읽기 능력과 텍스트 난이도를 같은 척도에 표시하는 상용 지표. 텍스트 측정은 어휘의 빈도와 문장 길이 같은 특성을 사용하며, 이 프로젝트의 가독성 공식 합성값은 공인 Lexile이 아니다.">Lexile</span>로 보간합니다. 그런데 이 공식들은 원래 긴 지문을 위한 것입니다. 문장 몇 개짜리 동화에서는 드문 장음절어 하나에도 학년이 튑니다. 공인 보정(MetaMetrics) 없이 만든 매핑이라 절대값도 계통적으로 높게 나옵니다. 목표 500L로 쓴 동화를 측정하면 중앙값이 868L입니다.

짧은 글에서 값이 불안정하다는 점은 Lexile을 만든 쪽도 수치로 밝히고 있습니다. 기술보고서에 따르면 약 125단어 슬라이스 하나의 표준오차가 178L이고, 4슬라이스짜리 책도 ±89L입니다. 전쟁과 평화처럼 4,082슬라이스는 돼야 ±3L로 내려갑니다.[^lexile] 우리 동화는 30~500단어라서, 처음부터 오차가 큰 구간에서 측정하고 있었습니다.

전면 재설계 대신 두 가지만 바꿨습니다. 이상치가 평균과 분산을 왜곡하지 않도록 합성 학년을 [0,14]로 클램프했고, 절대값 대신 <span class="term" data-tip="목표 레벨을 한 단계 바꿨을 때 측정 난이도가 실제로 몇 단계 움직였는지의 회귀 기울기. 1.0이면 지시한 만큼 정확히 반응한다는 뜻. 절대 눈금이 틀린 자로도 변화량은 잴 수 있다는 발상이다.">반응성 β</span>를 주 지표로 삼았습니다. β는 "레벨을 한 단계 낮춰 달라고 하면 실제로 한 단계 쉬워지는가"를 측정하는 회귀 기울기입니다. 눈금이 틀린 자로도 변화량은 잴 수 있습니다. 실측에서 β는 모든 모델에서 양수(+1.8~+3.2)였습니다. 모델들이 난이도 지시에 실제로 반응한다는 것까지는 확인했습니다.

## 3. 수정 중 다시 생긴 드리프트

2-2를 고치면서 파이썬 쪽 부트스트랩도 쌍 클러스터로 맞추려고 했습니다. 그러자 retire 스케줄러의 회귀 테스트가 깨졌습니다. 파이썬 retire의 결정적 테스트들(어느 배치에서 누가 은퇴하는지까지 고정)이 기존 <span class="term" data-tip="집계의 최소 단위. 한 쌍에 대한 한 심판의 판정 하나(양방향 평균을 마친 점수)를 말한다. 심판 셋이 본 쌍이면 contest 3개가 BT에 들어간다.">contest</span> 단위 CI에 맞춰져 있었기 때문입니다. CI 방식을 바꾸면 은퇴 시나리오 전체가 달라집니다.

그래서 당시에는 파이썬 수정을 되돌리고 앱(JS)만 쌍-군집으로 바꿨습니다. 2026-07-20 보정 때는 은퇴 판정 CI는 그대로 두고, Python과 앱의 공식 운영 구간만 쌍-군집으로 맞췄습니다. 프롬프트-군집 구간은 API 호출 없이 저장된 판정으로 계산하는 보고용 지표로만 추가했고, 프롬프트가 10개 미만이면 불안정 경고를 붙였습니다.

은퇴 판정 방식까지 바꾸려면 test_schedule 재보정과 50프롬프트 full 검증을 함께 진행해야 합니다. 이 작업은 아직 하지 못했습니다.

## 4. 검증

다섯 수정 모두 다시 실행해 볼 수 있도록 테스트를 남겼습니다.

- 앱 전체 JS 구문 검증. `<script>` 블록을 추출해 Node의 `vm.Script`로 파싱합니다. 3,400줄짜리 단일 파일에서는 오타 하나로 앱 전체가 빈 화면이 되기 때문에, 편집할 때마다 가장 먼저 실행하는 1차 관문으로 두었습니다.
- 변경한 순수 함수의 단위 테스트 13종. 파서는 과거에 잘못 파싱했던 사례들("Winner: Although...", "winner: a close call", `**A**` 볼드)을 회귀 케이스로 고정했습니다. 부트스트랩 테스트는 시드를 고정했을 때 결과가 같은지, 쌍 단위로 재표집하는지, 빈 입력을 처리하는지 확인합니다.
- 파이썬 테스트 확인. `python3 eval/tests/test_eval.py`(17개)와 `test_schedule.py`(6개)가 모두 통과했습니다. 파이썬 코드를 건드리지 않았다는 점도 테스트로 확인했습니다.
