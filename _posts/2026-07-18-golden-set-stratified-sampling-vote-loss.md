<span class="term" data-tip="Large Language Model. 많은 텍스트에서 토큰의 조건부 분포를 학습해 문장을 생성하거나 분류·요약·추론 작업을 수행하는 언어 모델을 뜻한다.">LLM</span> 심판을 믿어도 되는지는 같은 동화 쌍을 사람이 평가한 결과와 대조해야 알 수 있습니다. 그래서 사람과 LLM의 일치도(κ)를 재는 <span class="term" data-tip="사람이 직접 평가한 소량의 기준 데이터. 같은 항목을 자동(LLM) 평가와 사람이 모두 평가하게 한 뒤 일치도를 재면, 자동 평가를 얼마나 믿어도 되는지가 숫자로 나온다.">골든셋</span>을 만들었는데, 이 과정에서 문제가 두 번 생겼습니다. 아래에서는 표본 구성 방식을 고친 과정과, 평가 기록이 사라진 사고에 대응한 과정을 차례로 정리했습니다.

## 1. 표본 구성 문제

### 1-1. 층에서 주제가 빠져 있었습니다

수백 쌍을 사람이 모두 볼 수는 없습니다. 앱에는 원래 대표 표본 n쌍만 평가하는 기능이 있었습니다. (모델쌍 × 단어수 구간)으로 층을 나누고 <span class="term" data-tip="여러 목록을 돌아가며 하나씩 공평하게 뽑는 순회 방식. 각 목록의 비율을 자연스럽게 유지한다.">라운드로빈</span>으로 뽑는 방식이었습니다(3편). 실측 데이터로 다시 확인해보니 층 구성에 주제가 빠져 있었습니다.

이 시스템은 주제×테마×길이를 돌려 가며 프롬프트를 만듭니다. 즉 프롬프트 하나 안에서는 주제와 단어수가 고정됩니다. 그런데 층 목록을 삽입 순서대로 돌면, n이 작을 때 앞쪽 프롬프트의 주제와 길이로 표본이 몰립니다. 모델은 고르게 섞였는데 이야기는 전부 용 이야기가 될 수도 있는 구조였습니다.

### 1-2. 층 차원 추가와 순서 셔플

수정한 부분은 두 가지입니다.

1. 주제를 층 차원에 추가했습니다. 층 키는 (모델쌍 × 주제 × 단어수 구간) 3차원이 됩니다.
2. 층 순서를 <span class="term" data-tip="같은 입력과 상태에서 같은 결과를 내는 성질. 시드 고정은 난수 경로를 통제하는 한 조건일 뿐이며 구현·하드웨어·외부 서비스가 바뀌면 재현이 깨질 수 있다.">결정론적</span>으로 섞었습니다. 고정 시드 <span class="term" data-tip="배열의 뒤쪽부터 아직 확정되지 않은 위치 하나를 균등하게 골라 교환하는 셔플 알고리즘. 균등한 난수 생성기를 쓰면 모든 순열이 같은 확률로 나오며, 재현성은 난수 생성기와 구현까지 같아야 한다.">Fisher-Yates</span>로 층 배열을 섞은 뒤 라운드로빈을 돕니다. 시드가 고정이므로 결정론은 유지됩니다.

전체 알고리즘은 다음과 같습니다.

```text
strata ← 전체 쌍을 key = (sort(모델a,모델b), 주제, 단어수구간) 로 그룹화
strata를 key 사전순 정렬          # 삽입 순서 의존 제거
strata를 고정 시드로 셔플          # 주제·길이 군집 해체 (결정론 유지)
i ← 0; 선택 ← []
while |선택| < n:
    for 각 층 in strata:          # 라운드로빈
        층에 i번째 쌍이 있으면 선택에 추가; n 차면 종료
    i ← i + 1
```

라운드로빈은 층마다 고르게 뽑는 것을 보장합니다. 다만 앞쪽 n개를 어느 층부터 채울지는 층 순서가 정합니다. 주제와 길이가 프롬프트에 묶여 있는 구조에서는 순서를 먼저 흩어야 작은 n으로도 3차원을 고르게 덮을 수 있습니다. 실제로 차이를 만든 것은 셔플이었습니다.

결정론을 유지한 이유는 평가자 간 비교 때문입니다. 같은 데이터에 같은 n을 넣으면 난수 없이 항상 같은 표본이 나와야 여러 평가자가 같은 쌍을 봅니다. 그래야 그 위에서 κ와 α를 잴 수 있습니다. 표본을 30에서 50으로 늘려도 앞의 30쌍이 그대로 남는 중첩성이 필요한 것도 같은 이유입니다.

### 1-3. 797쌍으로 검증한 결과

797쌍 실측 데이터로 검증한 결과는 다음과 같습니다.

| n | 모델 커버 | 주제 커버 | 단어수 구간 커버 |
|---|---|---|---|
| 30 | 13/13 | 11/13 | 5/5 |
| 50 | 13/13 | 11/13 | 5/5 |
| 100 | 13/13 | 11/13 | 5/5 |

30쌍만 뽑아도 13개 모델과 5개 길이 구간이 모두 들어옵니다. 같은 n이면 같은 표본이 나오는지(결정론), n=30 표본이 n=50 표본 안에 그대로 포함되는지(중첩)도 함께 확인했습니다.[^strata]

### 1-4. 층화 표집이라는 이름과 근거

용어를 하나 짚고 넘어가겠습니다. 이 방식은 stratified k-fold 교차검증이 아닙니다. k개 폴드를 돌리는 CV는 하지 않았습니다. 폴드마다 비율을 보존한다는 층화 원리만 빌려 대표 부분집합 하나를 뽑았기 때문에 <span class="term" data-tip="모집단을 미리 정한 층으로 나눈 뒤 각 층에서 표본을 뽑는 방법. 중요한 하위 집단의 누락을 줄일 수 있지만 층 안의 대표성과 전체 가중치는 별도로 설계해야 한다.">층화 표집</span>(stratified sampling)이 맞는 이름입니다. 문서에도 "계열"이라고만 적었습니다. 사람에게 보여 줄 대표 표본을 뽑는 용도라 이 도구를 선택했습니다.

층화가 단순 무작위 추출보다 나은 이유는 통계학의 오래된 결과입니다. 층 안이 서로 비슷할수록(동질) 같은 표본 크기에서 추정 분산이 줄어듭니다. 최적 배분까지 가면 Neyman(1934)의 결과가 나오지만, 여기서는 비례 배분까지만 적용했습니다. 어느 모델, 주제, 길이도 빠지지 않게 하는 것이 목적이었기 때문에 그것으로 충분했습니다.

이 표본 위에서 재는 일치도 지표의 출처도 적어 둡니다. 2명 일치도 κ는 Cohen(1960), N명 일치도 α는 Krippendorff의 내용분석 방법론에서 왔습니다.[^kappa]

## 2. 투표 유실 사고

### 2-1. 원인 분석: human만 지우던 리셋 경로

그 30쌍을 평가하던 중이었습니다. 10쌍쯤 투표한 상태에서 다시 열어 보니 평가 기록이 사라져 있었습니다.

제 데이터가 날아간 사고였기 때문에 원인을 끝까지 추적했습니다. 앱 코드에서 투표(`STATE.human`)를 지우는 경로를 모두 찾아보니 실제로 있었습니다. 실측이 끝나거나 데모를 재생성할 때, 저장된 쌍과 현재 모델 목록이 맞지 않을 때 상태를 리셋하면서 `STATE.human`을 비우고 있었습니다. 새 결과를 받을 준비를 하는 코드가 이전 사람 투표까지 함께 지운 것입니다.

다행히 투표는 저장될 때 두 곳에 함께 기록됩니다. `STATE.human`(현재 평가자 화면용)과 `STATE.raters[평가자].votes`(평가자별 누적)입니다. 문제의 리셋 경로는 대부분 human만 지우고 raters는 남겨 두었습니다. 화면에서만 보이지 않을 뿐, 데이터는 남아 있을 가능성이 있었습니다.

### 2-2. 자동 복구 구현

복구 기능은 다음과 같이 구현했습니다.

- 앱을 시작할 때 `STATE.human`이 비어 있고, raters나 <span class="term" data-tip="브라우저가 출처별로 제공하는 비동기 객체 데이터베이스. localStorage보다 큰 구조화 데이터를 다루지만 저장 한도와 삭제 정책은 브라우저·디스크 여유·사용자 설정에 따라 달라진다.">IndexedDB</span> 백업에 현재 쌍과 맞는 투표가 남아 있으면 자동으로 복원합니다. 이어하기 지점은 아직 평가하지 않은 쌍부터 잡습니다.
- 이 시나리오를 단위 테스트로 고정했습니다. 30쌍 중 10표가 raters에만 남은 상태에서 복구하면 human에 10표가 돌아오고, 다음 평가 위치는 11번째가 됩니다. 9개 케이스가 모두 통과했습니다.[^recover]

다만 그 10표가 제 브라우저에서 실제로 돌아왔는지는 이 글을 쓰는 시점까지 확인하지 못했습니다. 에이전트로 브라우저 밖에서 Chrome의 로컬 저장소 파일(leveldb)을 직접 열어 보기까지 했지만, 값이 압축 블록 안에 있어 안전하게 꺼내지 못했습니다. 데이터가 남아 있었다면 복구 기능이 자동으로 되살립니다. 남아 있지 않았다면 아래 저장 구조를 만들기 전에 치른 비용입니다.

## 3. 투표 3중 저장과 GitHub 백업

이 사고 이후 사람 투표에는 저장 계층을 여러 겹 두었습니다. 투표 1건이 생기면 다음 세 곳에 기록됩니다.

| 저장 위치 | 기록 시점 | 특징 |
|---|---|---|
| localStorage | 즉시 | 빠름, 한도 약 10MB |
| IndexedDB | 즉시 | 사실상 무제한, 브라우저를 다시 켜도 남음 |
| GitHub | 버튼 1클릭 | `eval/runs/human/votes-<평가자>.json`으로 커밋 |

앱을 시작할 때 human이 비어 있으면 raters, 그다음 IndexedDB 순서로 자동 복구합니다. 리셋 경로에서는 raters(사람 투표)를 더 이상 지우지 않습니다.

GitHub 백업에는 목록 화면도 추가했습니다. 평가 화면에 들어가면 저장소에 있는 백업이 평가자, 표 수, 날짜와 함께 표시됩니다. 하나를 골라 이어서 평가하거나 새로 시작할 수 있습니다. 다른 컴퓨터에서도 자기 백업을 선택하면 아직 평가하지 않은 쌍부터 이어 갈 수 있습니다. 실측 결과(5편)와 마찬가지로 사람 투표도 GitHub 저장소를 백엔드로 쓰게 됐습니다.

5편의 <span class="term" data-tip="브라우저가 출처별로 제공하는 동기식 문자열 키-값 저장소. Web Storage 한도는 브라우저에 따라 다르고 한도를 넘으면 QuotaExceededError가 날 수 있어 큰 체크포인트 저장에는 맞지 않는다.">localStorage</span> 침묵 실패와 이번 투표 유실은 원인이 같았습니다. 브라우저 저장소 하나만 믿었습니다. LLM 판정은 비용이 드니 일찍 백업을 만들었고, 사람 투표는 몇 개 안 된다는 이유로 미뤘습니다. 그런데 이 시스템에서 다시 만들기 가장 비싼 데이터는 사람 투표였습니다. <span class="term" data-tip="소프트웨어가 다른 소프트웨어의 기능이나 데이터에 접근할 때 따르는 호출 계약. 사용할 주소, 입력 형식, 인증, 응답과 오류 규칙을 함께 정의한다.">API</span> 호출은 다시 돌리면 되지만, 사람에게 30쌍을 다시 읽어 달라고 할 수는 없습니다.

## 마치며

6월 16일 <span class="term" data-tip="평가할 기준과 각 기준의 판단 수준을 미리 적은 채점 지침. 이름만 나열하지 않고 기준 설명과 점수 앵커를 함께 줘야 평가자마다 뜻이 달라지는 문제를 줄일 수 있다.">루브릭</span> 문서 하나로 시작한 시리즈입니다. 한 달 반 동안 표준 라이브러리 기반 파이썬 파이프라인, 3,400줄 단일 <span class="term" data-tip="웹 문서의 구조와 의미를 요소로 표시하는 마크업 언어.
