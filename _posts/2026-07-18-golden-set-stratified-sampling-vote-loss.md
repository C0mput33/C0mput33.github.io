## 797쌍에서 30쌍을 고르다 생긴 구멍

수백 쌍을 사람이 다 볼 수는 없다. 앱에는 원래 대표 표본 n쌍만 평가하는 기능이 있었다. (모델쌍 × 단어수 구간)으로 층을 나누고 <span class="term" data-tip="여러 목록을 돌아가며 하나씩 공평하게 뽑는 순회 방식. 각 목록의 비율을 자연스럽게 유지한다.">라운드로빈</span>으로 뽑는 방식이었다(3편). 실측 데이터를 놓고 다시 보니 층에 주제가 빠져 있었다.

이 시스템은 주제×테마×길이를 돌려 가며 프롬프트를 만든다. 프롬프트 하나 안에서는 주제와 단어수가 고정된다는 얘기다. 그런데 층 목록을 삽입 순서대로 돌면, n이 작을 때 앞쪽 프롬프트의 주제와 길이로 표본이 몰린다. 모델은 고루 섞였는데 이야기는 전부 용 이야기일 수도 있었다.

두 군데를 고쳤다.

1. 주제를 층 차원에 넣었다. 층 키가 (모델쌍 × 주제 × 단어수 구간) 3차원이 됐다.
2. 층 순서를 <span class="term" data-tip="같은 입력과 상태에서 같은 결과를 내는 성질. 시드 고정은 난수 경로를 통제하는 한 조건일 뿐이며 구현·하드웨어·외부 서비스가 바뀌면 재현이 깨질 수 있다.">결정론적</span>으로 섞었다. 고정 시드 <span class="term" data-tip="배열의 뒤쪽부터 아직 확정되지 않은 위치 하나를 균등하게 골라 교환하는 셔플 알고리즘. 균등한 난수 생성기를 쓰면 모든 순열이 같은 확률로 나오며, 재현성은 난수 생성기와 구현까지 같아야 한다.">Fisher-Yates</span>로 층 배열을 섞은 다음 라운드로빈을 돈다. 시드가 고정이니 결정론은 깨지지 않는다.

알고리즘은 몇 줄이다.

```text
strata ← 전체 쌍을 key = (sort(모델a,모델b), 주제, 단어수구간) 로 그룹화
strata를 key 사전순 정렬          # 삽입 순서 의존 제거
strata를 고정 시드로 셔플          # 주제·길이 군집 해체 (결정론 유지)
i ← 0; 선택 ← []
while |선택| < n:
    for 각 층 in strata:          # 라운드로빈
        층에 i번째 쌍이 있으면 선택에 추가; n 차면 종료
    i ← i + 1
```

라운드로빈은 층마다 고르게 뽑아 주지만, 앞쪽 n개를 어느 층부터 채울지는 층 순서가 정한다. 주제와 길이가 프롬프트에 묶여 있으니 작은 n으로 3차원을 고루 덮으려면 순서부터 흩어 놓아야 했다. 실제로 차이를 만든 건 셔플이었다.

결정론을 지킨 건 평가자끼리 비교하려고서다. 같은 데이터에 같은 n을 넣으면 난수 없이 늘 같은 표본이 나와야 여러 평가자가 같은 쌍을 본다. 그래야 그 위에서 κ와 α를 잴 수 있다. 표본을 30에서 50으로 늘려도 앞의 30쌍이 그대로 남아야 하는 것(중첩성)도 같은 이유다.

797쌍 실측 데이터로 돌려 봤다.

| n | 모델 커버 | 주제 커버 | 단어수 구간 커버 |
|---|---|---|---|
| 30 | 13/13 | 11/13 | 5/5 |
| 50 | 13/13 | 11/13 | 5/5 |
| 100 | 13/13 | 11/13 | 5/5 |

30쌍만 뽑아도 13개 모델과 5개 길이 구간이 다 들어온다. 같은 n이면 같은 표본이 나오는지(결정론), n=30 표본이 n=50 표본 안에 그대로 들어가는지(중첩)도 확인했다.[^strata]

용어 하나는 짚고 넘어가야겠다. 이건 stratified k-fold 교차검증이 아니다. k개 폴드를 돌리는 CV는 안 했다. 폴드마다 비율을 보존한다는 층화 원리만 빌려서 대표 부분집합 하나를 뽑았으니 <span class="term" data-tip="모집단을 미리 정한 층으로 나눈 뒤 각 층에서 표본을 뽑는 방법. 중요한 하위 집단의 누락을 줄일 수 있지만 층 안의 대표성과 전체 가중치는 별도로 설계해야 한다.">층화 표집</span>(stratified sampling)이 맞는 이름이고, 문서에도 "계열"이라고만 적었다. 사람에게 보여 줄 대표 표본을 뽑는 일이라 이 도구를 골랐다.

층화가 단순 무작위보다 낫다는 근거는 통계학에 오래전부터 있다. 층 안이 서로 비슷할수록(동질) 같은 표본 크기에서 추정 분산이 줄어든다. 최적 배분까지 가면 Neyman(1934)의 결과가 나오는데, 나는 비례 배분에서 멈췄다. 어느 모델, 주제, 길이도 빠지지 않게 하는 게 목적이었으니 그걸로 충분했다. 여기서 재는 일치도 지표도 출처를 적어 둔다. 2명 일치도 κ는 Cohen(1960), N명 일치도 α는 Krippendorff의 내용분석 방법론에서 왔다.[^kappa]

## 평가해 둔 투표가 사라졌다

그 30쌍을 평가하던 중이었다. 10쌍쯤 투표하고 다시 열어 보니 평가가 없었다.

내 데이터가 날아간 일이라 원인을 끝까지 따라갔다. 앱 코드에서 투표(`STATE.human`)를 지우는 경로를 전부 뒤졌더니 실제로 있었다. 실측이 끝나거나 데모를 재생성할 때, 저장된 쌍과 현재 모델 목록이 안 맞을 때 상태를 리셋하면서 `STATE.human`을 비웠다. 새 결과를 받으려고 자리를 비우는 코드가 이전 사람 투표까지 같이 지우고 있었다.

다행히 투표는 저장될 때 두 곳에 같이 기록된다. `STATE.human`(현재 평가자 화면용)과 `STATE.raters[평가자].votes`(평가자별 누적)다. 문제의 리셋 경로는 대부분 human만 지우고 raters는 남겨 뒀다. 화면에서만 안 보일 뿐 데이터는 남아 있을 수도 있었다.

복구는 이렇게 만들었다.

- 앱을 켤 때 `STATE.human`이 비었는데 raters나 <span class="term" data-tip="브라우저가 출처별로 제공하는 비동기 객체 데이터베이스. localStorage보다 큰 구조화 데이터를 다루지만 저장 한도와 삭제 정책은 브라우저·디스크 여유·사용자 설정에 따라 달라진다.">IndexedDB</span> 백업에 현재 쌍과 맞는 투표가 남아 있으면 자동으로 복원한다. 이어하기 지점은 아직 안 한 쌍부터 잡는다.
- 이 시나리오를 그대로 단위 테스트로 고정했다. 30쌍 중 10표가 raters에만 남은 상태에서 복구하면 human에 10표가 돌아오고, 다음 평가 위치는 11번째가 된다. 9개 케이스가 모두 통과했다.[^recover]

그 10표가 내 브라우저에서 실제로 돌아왔는지는 이 글을 쓰는 지금도 모른다. 에이전트를 시켜 브라우저 밖에서 Chrome의 로컬 저장소 파일(leveldb)을 직접 뒤져 보기까지 했다. 값이 압축 블록 안에 있어서 안전하게 꺼내지 못했다. 남아 있었다면 복구 장치가 자동으로 되살린다. 남아 있지 않았다면 아래 저장 구조를 만들기 전에 낸 수업료다.

## 투표를 세 군데에 저장한다

이 일 뒤로 사람 투표에는 저장 계층을 여러 겹 깔았다. 투표 1건이 생기면 아래 세 곳에 기록된다.

| 저장 위치 | 기록 시점 | 특징 |
|---|---|---|
| localStorage | 즉시 | 빠름, 한도 약 10MB |
| IndexedDB | 즉시 | 사실상 무제한, 브라우저를 다시 켜도 남음 |
| GitHub | 버튼 1클릭 | `eval/runs/human/votes-<평가자>.json`으로 커밋 |

앱을 시작할 때 human이 비어 있으면 raters, 그다음 IndexedDB 순서로 자동 복구한다. 리셋 경로에서는 raters(사람 투표)를 더는 지우지 않는다.

GitHub 백업에는 목록 화면도 붙였다. 평가 화면에 들어가면 저장소에 있는 백업이 평가자, 표 수, 날짜와 함께 나온다. 하나를 골라 이어 하거나 새로 시작하면 된다. 다른 컴퓨터에서도 자기 백업을 누르면 안 한 쌍부터 이어 갈 수 있다. 실측 결과(5편)처럼 사람 투표도 GitHub 저장소를 백엔드로 쓰게 됐다.

5편의 <span class="term" data-tip="브라우저가 출처별로 제공하는 동기식 문자열 키-값 저장소. Web Storage 한도는 브라우저에 따라 다르고 한도를 넘으면 QuotaExceededError가 날 수 있어 큰 체크포인트 저장에는 맞지 않는다.">localStorage</span> 침묵 실패와 이번 투표 유실은 원인이 같았다. 브라우저 저장소 하나만 믿었다. LLM 판정은 돈이 드니까 일찍 백업을 깔아 놓고, 사람 투표는 몇 개 안 된다며 미뤘다. 그런데 이 시스템에서 다시 만들기 가장 비싼 데이터가 사람 투표였다. <span class="term" data-tip="소프트웨어가 다른 소프트웨어의 기능이나 데이터에 접근할 때 따르는 호출 계약. 사용할 주소, 입력 형식, 인증, 응답과 오류 규칙을 함께 정의한다.">API</span>는 다시 돌리면 그만이지만, 사람에게 그 30쌍을 다시 읽어 달라고 할 수는 없다.

## 시리즈를 닫으며

6월 16일 <span class="term" data-tip="평가할 기준과 각 기준의 판단 수준을 미리 적은 채점 지침. 이름만 나열하지 않고 기준 설명과 점수 앵커를 함께 줘야 평가자마다 뜻이 달라지는 문제를 줄일 수 있다.">루브릭</span> 문서 하나로 시작했다. 한 달 반 동안 표준 라이브러리로 짠 파이썬 파이프라인, 3,400줄짜리 단일 <span class="term" data-tip="웹 문서의 구조와 의미를 요소로 표시하는 마크업 언어. CSS는 표현을, JavaScript는 동작을 주로 담당한다.">HTML</span> 앱, 스케줄러 시뮬레이션, $46.76 레거시 실측 797쌍, <span class="term" data-tip="변경을 만든 쪽과 검토하는 쪽이 같은 대화 맥락을 공유하지 않게 분리하는 검토 방식. 검토자는 변경 내역과 검증 기준만 보고 판단한다.">교차 리뷰</span>와 리플레이 검증까지 만들었다. 비용 절감 25~58%는 같은 저장 데이터를 다시 돌린 리플레이 결과다. 바깥 데이터에서도 정확도가 유지된다는 보장은 없다.

기술적인 결론은 각 편에 적었으니 여기서는 과정 얘기만 하겠다. 제일 위험했던 건 크래시보다 아무 표시 없이 틀리는 경우였다. 좁게 나온 <span class="term" data-tip="Confidence Interval의 약칭. 이 글에서는 추정 불확실성을 나타내는 신뢰구간을 뜻하며 CI/CD의 CI와는 다른 용어다.">CI</span>, 기록되지 않은 tie, 0으로 찍히는 지표가 다 그랬다. 작업의 절반은 그런 걸 눈에 보이게 만드는 데 들어갔다(텔레메트리, 검증 스크립트, 근거 전문 공개). <span class="term" data-tip="같은 절차로 표본을 반복 수집할 때 정해진 비율만큼 모수를 포함하도록 만든 구간. 두 개의 95% 신뢰구간이 겹치는지만으로 차이의 유의성을 판정할 수는 없다.">신뢰구간</span>을 정직하게 계산하니 비용이 붙었고, 그 비용은 표집을 바꿔서 줄였다. 심판에게 자기평가를 금지한 논리는 내 코드에도 처음부터 똑같이 적용했어야 했다.

다음 실측은 자기평가 제외, `strict-v2` 파싱, <span class="term" data-tip="다음 토큰 확률분포의 평탄함을 조절하는 값. 낮을수록 높은 확률의 토큰에 집중하지만 temperature 0도 제공자·모델·실행 환경에 따라 완전한 재현성을 보장하지 않는다.">temperature</span> 0 심판, 쌍-군집 운영 CI로 새 런을 시작할 계획이다. temperature 0은 샘플링 변동을 줄여 주지만 같은 출력이 완전히 재현된다는 보장은 없다. 프롬프트-군집 CI는 보고용으로 같이 계산한다.
