[2편](/posts/llm-eval-pipeline-from-scratch-bradley-terry/)에서 파이썬 평가 파이프라인을 만들었다. 그 파이프라인을 커밋한 6월 18일, 480줄짜리 <span class="term" data-tip="웹 문서의 구조와 의미를 요소로 표시하는 마크업 언어. CSS는 표현을, JavaScript는 동작을 주로 담당한다.">HTML</span> 파일도 같이 커밋했다.[^v1] 한 달 뒤 이 파일은 3,400줄이 됐다. 프론티어 모델 13개의 실측 평가를 통째로 브라우저 안에서 돌리는 엔진이 돼 있었다.

같은 걸 왜 두 번 만들었는지, 그러고 나서 뭘 겪었는지 적어 둔다.

## 파이썬으로는 안 되는 게 하나 있었다

이 평가 시스템에서 <span class="term" data-tip="Large Language Model. 많은 텍스트에서 토큰의 조건부 분포를 학습해 문장을 생성하거나 분류·요약·추론 작업을 수행하는 언어 모델을 뜻한다.">LLM</span> 심판의 순위는 절반이다. 나머지 절반은 사람 <span class="term" data-tip="사람이 직접 평가한 소량의 기준 데이터. 같은 항목을 자동(LLM) 평가와 사람이 모두 평가하게 한 뒤 일치도를 재면, 자동 평가를 얼마나 믿어도 되는지가 숫자로 나온다.">골든셋</span>이다. 같은 동화 쌍을 사람도 평가하고 심판과의 일치도(Cohen's κ)를 재야 심판을 믿어도 되는지 말할 수 있다.

그 사람이 나 혼자가 아니었다. 멘토님과 팀원, 나중에는 학부모까지 평가에 들어올 수 있어야 했다. 그분들께 Python을 깔고 터미널에서 스크립트를 돌려 달라고 할 수는 없다.

요구사항은 하나만 정했고, 결국 그게 아키텍처가 됐다.

> 파일 1개. 빌드·서버·의존성 없음. 더블클릭하면 바로 열린다.[^appreadme]

React도 빌드 도구도 안 썼다. `index.html` 하나에 순수 JS로 UI와 통계 엔진(Bradley-Terry, 부트스트랩, κ)을 다 넣었다. 메신저로 파일을 보내면 받은 사람 브라우저에서 그대로 돈다. 보내는 게 배포다. <span class="term" data-tip="소프트웨어가 다른 소프트웨어의 기능이나 데이터에 접근할 때 따르는 호출 계약. 사용할 주소, 입력 형식, 인증, 응답과 오류 규칙을 함께 정의한다.">API</span> 키가 없어도 고정 시드 합성 데이터로 전체 흐름이 도는 데모 모드를 기본으로 깔아서, 처음 여는 사람도 30초 안에 평가 방식을 만져 볼 수 있다.

단일 파일이 커지면 모놀리스가 된다는 건 알고 시작했다. 지금 3,420줄이다. 그 값을 치른 얘기는 6편에 있다.

완성된 구조부터 보여 주는 게 빠르겠다. 아래 그림이 이 앱의 실측 경로 전부고, 뒤에 이어지는 편들은 대부분 이 상자 중 하나가 왜 이렇게 생겼는지에 관한 얘기다.

- 설정: 평가할 모델 N개와 심판 <span class="term" data-tip="서로 다른 회사 계열의 심판 여러 명을 함께 쓰는 구성. 심판마다 취향과 편향이 다른데, 계열을 섞으면 한 심판의 성향이 순위를 좌우하는 걸 줄일 수 있다.">jury</span>, 동화 권수, 예산 상한, 스케줄(full 또는 <span class="term" data-tip="이 프로젝트의 은퇴 스케줄러. 배치(5권)마다 BT와 CI를 갱신하고, CI 분리가 2연속 확인된 모델만 은퇴시킨다. 한 번의 우연으로 탈락시키지 않는 확인 절차가 이름의 유래다.">retire2</span>)을 고른다. 시작 전에 고른 모델 전부에 테스트 호출을 보내 모델명(slug)이 실제로 있는지 본다. 비싼 호출 앞에 싼 점검을 둔 사연은 바로 아래에 있다.
- 생성: 프롬프트마다 생존 모델이 동화를 한 편씩 쓴다. `childlit-v3` 본선 user prompt에는 주제·형식·길이·독서 방식·목표 연령만 넣고 수치 <span class="term" data-tip="영어 독자의 읽기 능력과 텍스트 난이도를 같은 척도에 표시하는 상용 지표. 텍스트 측정은 어휘의 빈도와 문장 길이 같은 특성을 사용하며, 이 프로젝트의 가독성 공식 합성값은 공인 Lexile이 아니다.">Lexile</span>은 넣지 않는다. 요청 길이에 맞춘 출력 <span class="term" data-tip="모델의 토크나이저가 텍스트를 나눈 처리 단위. 한 토큰은 단어 하나와 같지 않으며 같은 문장도 모델별 토크나이저에 따라 토큰 수가 달라질 수 있다.">토큰</span> 상한을 두고, 창작은 <span class="term" data-tip="다음 토큰 확률분포의 평탄함을 조절하는 값. 낮을수록 높은 확률의 토큰에 집중하지만 temperature 0도 제공자·모델·실행 환경에 따라 완전한 재현성을 보장하지 않는다.">temperature</span> 0.7로 돌린다. 이미지나 그림 지시, 페이지 메모가 섞인 출력은 생성 실패로 뺀다. 사람 검토용 한국어 번역은 순위에 안 쓴다. 수치 Lexile은 별도 <span class="term" data-tip="아이가 어른의 실시간 도움이나 낭독 없이 직접 글자를 해독하고 내용을 이어 가는 읽기 방식. 같은 아이도 읽어주는 글을 이해하는 수준과 혼자 읽는 수준이 다를 수 있다.">독립 읽기</span> 프로브에서만 쓴다.
- 판정: 생존자끼리 나오는 모든 쌍을 심판마다 두 번(A,B와 B,A) 묻는다. 샘플링 변동을 줄이려고 temperature 0을 쓰지만 완전히 결정적이라고 가정하지는 않는다. 심판이 후보와 같은 계열이면 그 쌍에서 빠진다. 응답에서 승자를 못 읽으면 몰래 무승부로 넘기지 않고 실패로 세서 화면에 띄운다.
- 배치 경계(retire2): 5권마다 <span class="term" data-tip="맞대결 승패만으로 각 후보의 숨은 실력을 추정하는 통계 모델(1952). 실력 차가 승률을 정한다고 가정하고, 관측된 모든 승패를 가장 잘 설명하는 실력값을 최우도로 찾는다. 경기 순서와 무관하게 같은 답이 나오는 배치 방식이라, 고정된 대전 기록의 순위에 적합하다.">Bradley-Terry</span>를 다시 적합하고 쌍 클러스터 <span class="term" data-tip="가진 데이터에서 복원추출로 여러 번 가짜 표본을 만들어 같은 계산을 반복하고, 그 결과들의 흩어짐으로 추정치의 불확실성을 재는 방법. 표본이 모집단을 대표한다면 재표집의 흔들림이 실제 추정 오차와 비슷하다는 원리다.">부트스트랩</span>으로 95% <span class="term" data-tip="Confidence Interval의 약칭. 이 글에서는 추정 불확실성을 나타내는 신뢰구간을 뜻하며 CI/CD의 CI와는 다른 용어다.">CI</span>를 갱신한다. CI가 2연속 분리된 모델은 은퇴하고, 은퇴자도 그 시점 점수로 리더보드에 남는다. 다음 배치에는 생존자만 간다.
- 결과: 주 순위는 Arena(<span class="term" data-tip="Bradley–Terry 모델의 약칭. 두 후보의 상대적 실력으로 맞대결 승률을 설명하고 전체 pairwise 결과에서 실력값을 추정한다.">BT</span>)와 CI, 보조로 <span class="term" data-tip="경기가 끝날 때마다 결과와 기대승률의 차이만큼 점수를 즉시 조정하는 체스식 레이팅. 실력이 변하는 선수를 추적하는 데 좋지만, 경기 순서에 따라 최종 값이 달라져 고정된 대전 기록의 순위에는 부적합하다.">Elo</span>를 보여 준다. 축별 진단, 자기 계열 편향 카드, 자동 <span class="term" data-tip="글을 얼마나 수월하게 읽고 이해할 수 있는지를 뜻한다. 문장·단어 표면값으로 계산한 가독성 공식은 정량 단서일 뿐 의미 구조, 배경지식, 독자와 읽기 목적 전체를 대신하지 않는다.">가독성</span> 프록시, 선택형 난이도 <span class="term" data-tip="목표 레벨을 한 단계 바꿨을 때 측정 난이도가 실제로 몇 단계 움직였는지의 회귀 기울기. 1.0이면 지시한 만큼 정확히 반응한다는 뜻. 절대 눈금이 틀린 자로도 변화량은 잴 수 있다는 발상이다.">반응성 β</span>까지 한 화면에 있다. 자동 난이도 수치는 BT와 은퇴 판정에 안 쓴다. 실측이 끝나면 report.html과 results.json이 GitHub에 아카이브된다. 세 경로의 관계는 [2트랙 아키텍처 글](/posts/creative-ranking-reading-level-two-track/)에 따로 적었다.
- 저장 계층: 진행 상태는 1.5초마다 <span class="term" data-tip="브라우저가 출처별로 제공하는 동기식 문자열 키-값 저장소. Web Storage 한도는 브라우저에 따라 다르고 한도를 넘으면 QuotaExceededError가 날 수 있어 큰 체크포인트 저장에는 맞지 않는다.">localStorage</span>에 저장하고, 10MB 한도를 넘으면 바로 <span class="term" data-tip="브라우저가 출처별로 제공하는 비동기 객체 데이터베이스. localStorage보다 큰 구조화 데이터를 다루지만 저장 한도와 삭제 정책은 브라우저·디스크 여유·사용자 설정에 따라 달라진다.">IndexedDB</span>로 넘어간다. 10쌍마다 IndexedDB와 GitHub에 자동 백업도 한다. 유실 사고를 두 번 겪고 나서 이렇게 됐다(5편, 8편).
- 사람 골든셋: 층화 표본으로 뽑은 쌍을 사람이 평가하고, pair_id로 심판 판정과 짝지어 일치도(κ, α)를 잰다.
- 파이썬 미러: 같은 수식을 파이썬으로도 유지한다. 두 구현이 같은 입력에 같은 순위를 내는지는 등가성 테스트로 확인한다.

그림에 적은 건 [index.html](https://github.com/C0mput33/little-bard/blob/main/eval/app/index.html)에서 직접 볼 수 있다. 판정의 `{temp: 0}`, 부트스트랩 `iters=1000`, 쌍 단위 재표집, 1.5초 저장, 10쌍마다 백업, 자기 계열 제외 기본값이 전부 이 파일 하나에 있다.

파일은 하나지만 안에서는 네 덩어리로 나눠 짰다. 생성·판정 호출과 재시도를 맡는 신호 수집, 집계와 은퇴를 맡는 통계, 3중 저장을 맡는 영속성, 사람 골든셋과 파이썬 미러로 맞춰 보는 검증이다. 뒤에 나오는 수정도 대부분 이 경계 중 한 곳에서 일어났다.

## 첫 실측은 시작하자마자 실패했다

6월 19일, 처음으로 실제 API(OpenRouter)를 붙여 실측을 돌렸다. 실패했다. 원인을 찾고 나니 허무했다. 모델 목록에 넣어 둔 <span class="term" data-tip="API에서 모델을 지정하는 고유 식별 문자열(예: openai/gpt-5.2). 오타가 나면 호출 시점에야 404로 드러난다.">slug</span> 6개가 <span class="term" data-tip="여러 회사의 LLM을 하나의 API와 결제로 호출하게 해주는 중계 서비스. 모델마다 계정을 따로 만들 필요가 없어 다모델 비교 실험에 편하다.">OpenRouter</span>에 없는 이름이었다.[^slugfix]

모델 카탈로그를 문서와 기억만 믿고 적었다. 없는 모델명은 호출하는 순간 404가 나야 알 수 있고, 그때는 이미 다른 모델 호출에 돈을 쓴 뒤다.

고친 건 두 가지다.

1. 사전 점검. 실측 전에 고른 모델 전부에 1토큰짜리 테스트 호출을 보내 slug가 유효한지 본다. 실패한 모델을 한꺼번에 보여 주고 시작을 막는다.
2. 에러 상세화. <span class="term" data-tip="클라이언트와 서버가 요청과 응답을 주고받는 웹 전송 규약. 메서드, 상태 코드, 헤더와 본문 형식을 정의하며 TLS를 사용한 암호화 연결은 HTTPS라고 부른다.">HTTP</span> 상태 코드별로 원인을 사람 말로 풀어 준다. 401은 키 오류, 402는 크레딧 부족, 404는 slug 없음, 429는 요청 한도다.

둘 다 처음부터 있었어야 했다. "일단 돌려 보자"로 짠 코드라 빠져 있었다. 같은 날 <span class="term" data-tip="같은 두 답을 A/B와 B/A 순서로 각각 평가해 순서에 따른 변화를 확인하는 방법. 두 결과를 함께 쓰면 위치 편향을 줄일 수 있지만 완전히 없어진다고 보장되지는 않는다.">양방향 swap</span>(위치 편향 통제)도 앱에 넣었다.

## 같은 데이터인데 순위가 달랐다

6월 23일, 같은 판정 데이터를 넣었는데 앱과 파이썬의 순위가 미묘하게 달랐다. swap 집계 방식이 문제였다. 파이썬은 (쌍, 심판)마다 정방향과 역방향 판정을 평균해 <span class="term" data-tip="집계의 최소 단위. 한 쌍에 대한 한 심판의 판정 하나(양방향 평균을 마친 점수)를 말한다. 심판 셋이 본 쌍이면 contest 3개가 BT에 들어간다.">contest</span> 하나로 만든다. 앱은 두 판정을 따로 넣고 있었다.[^swapfix]

정방향과 역방향을 contest 두 개로 넣으면 <span class="term" data-tip="내용과 무관하게 먼저 보여준 답을 더 좋게 평가하는 경향. LLM 심판에게 일관되게 관측되는 대표적 편향이라, 순서를 바꿔 두 번 묻는 통제가 필요하다.">위치 편향</span> 때문에 생긴 "정방향 A승, 역방향 B승"이 실력 신호처럼 우도에 두 번 들어간다. (쌍, 심판) 단위로 먼저 평균해서 contest 하나(s ∈ {0, ¼, ½, ¾, 1})로 접어야 위치 효과가 그 안에서 상쇄된다. 파이썬은 처음부터 이렇게 했고 앱만 어긋나 있었다.

앱을 파이썬 쪽에 맞췄다. 그리고 같은 judgments를 양쪽 엔진에 넣어 <span class="term" data-tip="이 시스템의 최종 점수. BT로 추정한 실력값을 체스 레이팅처럼 읽히도록 평균 1000 기준으로 변환한 것. 두 모델의 점수 차가 곧 승률로 환산된다(차이 100이면 약 64%, 400이면 약 91%).">Arena 점수</span>를 대조하는 등가성 테스트를 만들었다.

엔진 하나를 두 언어로 들고 가는 게 공짜가 아니라는 걸 이때 처음 느꼈다. 한쪽을 고치고 다른 쪽을 잊으면 아무 경고도 없이 갈라진다. 6편(심판 temperature)과 7편(부트스트랩 방식)에서 똑같은 일을 두 번 더 겪었다.

## 사람 평가 기능은 이틀 사이에 다 붙었다

애초에 사람 평가 때문에 만든 앱이라 이 부분이 제일 많이 바뀌었다. 커밋이 6월 23일과 24일 이틀에 몰려 있다.

| 기능 | 왜 필요했나 |
|---|---|
| 다중 평가자 (rater별 누적·전환) | 한 노트북으로 여러 명이 돌아가며 평가하는 상황 |
| 팀 분산 평가 (HTML을 나눠 주고 결과 파일 병합) | 각자 자기 컴퓨터에서 평가하고 jsonl로 합치기 |
| 평가자 신뢰도 종합 (<span class="term" data-tip="평가자 수가 일정하지 않거나 일부 판정이 비어 있어도 계산할 수 있는 신뢰도 계수. 자료 척도에 맞는 불일치 함수를 쓰며 1은 완전 일치, 0은 우연 기대 수준이다.">Krippendorff α</span>) | 2명은 <span class="term" data-tip="두 평가자의 범주형 판정 일치도에서 주변분포로 기대되는 우연 일치를 보정한 계수. 1은 완전 일치, 0은 기대 일치 수준이며 음수도 가능하다.">Cohen's κ</span>로 되지만 N명 일치도는 α가 필요[^alpha] |
| 부분 평가 (대표 표본만) | 쌍이 수백 개면 다 못 본다. 모델×단어수 비율을 유지한 층화 표본 |
| 실측 비용·ETA·예산 상한 | 실측은 돈이라, 예산을 넘으면 자동 중단 |

층화 표본은 난수 없이 <span class="term" data-tip="같은 입력과 상태에서 같은 결과를 내는 성질. 시드 고정은 난수 경로를 통제하는 한 조건일 뿐이며 구현·하드웨어·외부 서비스가 바뀌면 재현이 깨질 수 있다.">결정론적</span>으로 뽑는다. 같은 데이터에 같은 n을 주면 늘 같은 표본이 나온다. 평가자끼리 일치도를 재려면 다들 같은 쌍을 봐야 해서 이렇게 했다.

상태 설계도 이때 굳었다. 앱 상태는 전부 `STATE` 객체 하나에 넣었고, 거기서 갈라지는 저장 단위가 그대로 데이터 모델이 됐다.

| 상태 | 담는 것 | 분리한 이유 |
|---|---|---|
| `pairs[]` | 쌍별 동화 원문(EN/KO)과 심판별 점수·근거 전문 | 분석과 리포트의 원시 데이터. 근거 전문 보존이 원칙 |
| `human` / `raters` | 현재 평가자 화면용 투표 / 평가자별 누적 투표 | 여러 명이 한 앱을 쓰니 화면과 장부를 분리 |
| `live` | 실측 진행 <span class="term" data-tip="진행 상태를 통째로 저장해둔 지점. 중단되거나 크레딧이 떨어져도 완료분을 다시 호출하지 않고 그 지점부터 이어서 실행할 수 있다.">체크포인트</span>(생성물·판정 캐시·은퇴 상태) | 중단 지점부터 재개하려면 완료분과 진행분이 달라야 함 |
| `usage` / `modelCost` | 콜·토큰·비용 누적, 모델별 편당 비용 | 예산 가드와 품질×비용 분석의 입력 |
| `reviewIds` | 층화 표본으로 고른 쌍 id | 평가 범위 자체도 상태다. 새로고침에도 유지돼야 함 |

이렇게 나눠 둔 덕을 두 번 봤다. 6월 28일 크레딧이 떨어져 실측이 멈췄을 때, `live`의 판정 캐시가 있어서 끝난 부분을 다시 호출하지 않아도 됐다. 투표가 화면에서 사라진 날에도 `raters` 장부에는 남아 있었다(8편).

## 첫 완주, 그리고 GitHub를 백엔드로

6월 24일, 처음으로 실측을 끝까지 돌렸다. 8모델 × 5심판, 84/84쌍이었다.[^firstrun] 끝내고 보니 결과가 브라우저 localStorage에만 있었다. 노트북을 바꾸면 세션이 없다.

그래서 앱에서 GitHub API로 세션 <span class="term" data-tip="문자열·숫자·불리언·배열·객체·null을 표현하는 텍스트 데이터 형식. 주석과 trailing comma는 표준 JSON에 포함되지 않는다.">JSON</span>을 바로 커밋하게 했다. 서버 없이 GitHub 저장소를 백엔드처럼 썼다. 다음 날 막혔다. GitHub Contents API는 이 방식으로 1MB 넘는 파일을 못 읽는데, 동화 원문이 쌓인 세션은 금방 1MB를 넘는다. Blob API로 넘어가는 폴백을 넣어서 풀었다.[^blob]

6월 28일에는 <span class="term" data-tip="오픈 웨이트 모델을 로컬 장비에서 내려받아 실행하고 API로 호출하게 해주는 도구. 외부 모델 API의 호출 요금은 없지만 장비·전력·운영 비용은 별도다.">Ollama</span>를 붙여 로컬 모델도 평가할 수 있게 했다(비용 0). 클라우드 프론티어 모델과 내 컴퓨터의 2B급 온디바이스 모델을 같은 잣대로 재 보고 싶었다. 그날 14모델 실측은 180/273쌍에서 크레딧이 떨어져 멈췄는데, 체크포인트 이어하기를 미리 만들어 둔 터라 버린 호출은 없었다.

## 근거를 다 남기기로 했다

이 기간 커밋을 다시 훑어보니 하는 일이 거의 같았다. 판정 근거와 실제로 보낸 프롬프트를 빠짐없이 남겨서, 승인된 검토자가 나중에 감사할 수 있게 만드는 일이다. 2026-07-20에 확인했을 때 little-bard 저장소는 비공개였고, 아래 GitHub 링크는 권한이 없으면 404가 뜬다. 공개 검증이라고 하려면 비식별 자료를 따로 내놔야 한다.

- 각 쌍을 어느 모델이 만들었는지, 심판별 판정과 근거 전문(정방향·역방향 원문 그대로)
- 생성과 심판에 실제로 보낸 프롬프트 원문
- 앱 안 코드·프롬프트 탭에 통계 엔진 코드 자체를 띄우고, 원리 탭에 설계 결정의 근거와 출처를 문서화

멘토님께 이 평가를 믿어도 되는지 검증받아야 했다. 결과 숫자만 보여 드려서는 검증이 안 된다. 판정 근거 원문이 열려 있어야 "심판이 이상한 이유로 이겼다고 하네" 같은 걸 찾을 수 있다. 나중에 심판 파싱 버그와 편향을 데이터로 잡은 것도 이렇게 열어 둔 덕이다.
